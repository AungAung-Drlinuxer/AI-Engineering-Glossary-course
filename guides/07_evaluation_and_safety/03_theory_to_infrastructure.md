# 03 — သီအိုရီမှ ထုတ်လုပ်မှု အခြေခံအဆောက်အအုံသို့ (Theory to Infrastructure)

ဤစာတမ်းသည် နယ်ပယ် ၀၇ ၏ term ၁၇ ခုလုံးကို အခြေခံအဆောက်အအုံ အမြင်ဖြင့် ပြန်လည် ဖတ်သည်။ Evaluation term တစ်ခုသည် စာတမ်းအတွင်း သီအိုရီ အဖြစ်သာ မကျန်ရပါ။ ၎င်းသည် eval run တစ်ခုလျှင် token နှင့် USD ပမာဏ၊ သိမ်းဆည်းရသည့် byte ပမာဏ၊ guardrail တစ်ခုက request လမ်းကြောင်း အတွင်း ထည့်သည့် မီလီစက္ကန့်၊ monitoring pipeline တစ်ခု အကဲဖြတ်နိုင်သည့် sample အရေအတွက် သို့မဟုတ် ထုတ်လုပ်မှုတွင် ကျိုးပျက်မည့် အချက် အနက် တစ်ခုခုကို ရွေ့လျားစေသည်။ ရွေ့လျားသည့် ကိန်းဂဏန်း တစ်ခုစီသည် တုံ့ပြန်ရမည့် ဆုံးဖြတ်ချက် တစ်ခုစီနှင့် တွဲလျက် ရှိသည်။

ဤစာတမ်းရှိ ကိန်းဂဏန်း အားလုံးသည် `guides/07_evaluation_and_safety/scripts/` အောက်ရှိ Python script များမှ ရရှိသည့် တန်ဖိုးများ ဖြစ်သည်။ ဖော်ပြသည့် တန်ဖိုး အားလုံးသည် ဖော်မြူလာ နှင့် ယူဆချက် (assumption) မှ တွက်ချက်ထားသည့် တန်ဖိုးများ ဖြစ်ပြီး တိုင်းတာမှု (benchmark) ရလဒ် များ မဟုတ်ပါ။ စျေးနှုန်း၊ request rate နှင့် model အရွယ်အစားတို့သည် vendor၊ hardware နှင့် deployment အခြေအနေအလိုက် ကွာခြားသည့်အတွက် ထို တန်ဖိုး တိုင်းကို `တန်ဖိုးသည် အခြေအနေအလိုက် ကွာခြားသည်` ဟု မှတ်သားထားသည်။

Evaluation နှင့် safety ကို သီးခြား မခွဲနိုင်ပါ — တိုင်းတာမှု မရှိပါက ဘေးကင်းရေးကို သက်သေပြရန် ခက်ခဲပြီး ဘေးကင်းရေး စဉ်းစားချက် မရှိပါက တိုင်းတာမှု ရလဒ်သည် ထုတ်လုပ်မှု အရည်အသွေးကို မဖော်ပြနိုင်ပါ။ ထို့ကြောင့် ဤနယ်ပယ်၏ ဝင်ရိုးများသည် ကုန်ကျစရိတ် နှင့် အန္တရာယ် နှစ်ခုလုံးကို တစ်ပြိုင်နက် ရွေ့လျားစေသည်။

## ၁။ ဝင်ရိုး ခြောက်ခု၏ ဝေါဟာရ သတ်မှတ်ချက်

နောက်ပိုင်း အပိုင်းများတွင် ဤဝေါဟာရ ခြောက်ခုကို တူညီသည့် အဓိပ္ပာယ်ဖြင့်သာ အသုံးပြုမည် ဖြစ်သည်။

**eval compute and cost** — eval set တစ်ခုကို အကဲဖြတ်ရာတွင် သုံးစွဲသည့် model call၊ scorer နှင့် judge token ပမာဏ ဖြစ်သည်။ ဤဝင်ရိုးတွင် ကိန်းသည် token အရေအတွက် ဖြစ်ပြီး token တိုင်းသည် accelerator အချိန် နှင့် စျေးနှုန်း အပေါ် တိုက်ရိုက် ရောက်သည်။ ထို့ကြောင့် ဤဝင်ရိုးသည် ခန့်မှန်းနိုင်မှု အမြင့်ဆုံး ကုန်ကျစရိတ် အမျိုးအစား ဖြစ်သည်။

**data storage** — version စီမံထားသည့် eval set၊ trace၊ judge verdict နှင့် model card အစရှိသည့် byte ပမာဏ ဖြစ်သည်။ eval set တိုင်းကို version တစ်ခုစီဖြင့် သိမ်းဆည်းပြီး ရလဒ် တိုင်းကို ထို version နှင့် တွဲဖက် မှတ်တမ်းတင်ရမည်။ Storage သည် ငွေ အနည်းငယ်သာ ကုန်ကျသော်လည်း မှတ်တမ်း မပြန်ရှာနိုင်ခြင်းသည် ရလဒ် တစ်ခုလုံးကို ယုံထိုက်မှု မရှိစေပါ။

**latency of a guardrail in the request path** — request တစ်ခုစီ အတွင်း synchronously run သည့် guardrail က ထည့်သည့် မီလီစက္ကန့် ဖြစ်သည်။ ဤဝင်ရိုးရှိ ကိန်းသည် guardrail ၏ service time နှင့် queueing အကျိုးဆက် နှစ်ခုလုံးကို ပေါင်းထားသည်။ guardrail သည် တူညီသည့် worker များ၏ စွမ်းရည် ကိုလည်း စားသည့်အတွက် latency နှင့် throughput ကို အတူတကွ တွက်ရမည်။

**throughput of continuous evaluation** — monitoring pipeline တစ်ခုက အချိန် တစ်ခုအတွင်း အကဲဖြတ်နိုင်သည့် sample အရေအတွက် သို့မဟုတ် window အရေအတွက် ဖြစ်သည်။ window သေးလျှင် standard error ကြီးပြီး ဖော်ထုတ်နိုင်မှု ကျသည်၊ window ကြီးလျှင် ဖော်ထုတ်နိုင်မှု တိုးသော်လည်း သတိပေးချက် နောက်ကျသည်။ ဤဝင်ရိုးသည် ဖော်ထုတ်နိုင်မှု နှင့် ဖော်ထုတ်ရန် ကြာသည့် အချိန် အကြား လဲလှယ်မှု ဖြစ်သည်။

**cost per eval run** — eval set တစ်ခုလုံးကို တစ်ကြိမ် run သည့် USD ပမာဏ ဖြစ်သည်။ token ကုန်ကျစရိတ်၊ judge ကုန်ကျစရိတ် နှင့် လူသား ပြန်လည်စစ်ဆေးမှု ကုန်ကျစရိတ် သုံးခု ပါဝင်သည်။ run အရေအတွက် (commit တိုင်း၊ ညတိုင်း၊ release တိုင်း) နှင့် မြှောက်လျှင် နယ်ပယ်၏ လစဉ် ကုန်ကျစရိတ် ရသည်။

**production consequence** — ထို concept ကို လျစ်လျူရှုလျှင် ထုတ်လုပ်မှုတွင် မည်သည့် အရာ ကျိုးပျက်မည်ကို ဆိုလိုသည်။ ဥပမာ guardrail ကို နုတ်ပစ်လျှင် ကျိုးပျက်သည့် အရာသည် latency မဟုတ်ဘဲ injection မှ ရောက်လာသည့် tool အလွဲသုံးမှု ဖြစ်သည်။ ဤဝင်ရိုးသည် အခြား ဝင်ရိုး ငါးခုလုံးကို ဆုံးဖြတ်ချက် အဆင့်သို့ ပြောင်းလဲပေးသည်။

## ၃။ term အလိုက် ရှင်းလင်းချက်

term များကို မိသားစု ငါးခုဖြင့် စုစည်းထားသည် — (က) တိုင်းတာမှု အခြေခံ၊ (ခ) ရမှတ် တိုင်းတာသည့် metric များ၊ (ဂ) အကဲဖြတ်သူ နှင့် အရည်အသွေး၊ (ဃ) ထိန်းချုပ်မှုများ၊ (င) ကိုက်ညီမှု နှင့် စောင့်ကြည့်ခြင်း။ ဤအုပ်စုခွဲမှုသည် အပိုင်း ၂ ၏ ဇယားနှင့် တိုက်ရိုက် ကိုက်ညီသည်။

### မိသားစု (က) — တိုင်းတာမှု အခြေခံ (measurement foundations)

#### Evaluation (Eval)

Evaluation သည် ရှင်းလင်းသည့် အောင်မြင်မှု စံနှုန်းများ၊ data၊ scorer များနှင့် ပြန်လည်စစ်ဆေးသည့် လုပ်ထုံးလုပ်နည်းများကို အသုံးပြု၍ ကိုယ်စားပြုသည့် အလုပ်များတွင် စနစ်၏ အပြုအမူကို တိုင်းတာသည့် လုပ်ငန်းစဉ် ဖြစ်သည်။ အခြေခံအဆောက်အအုံ အမြင်ဖြင့် ၎င်းသည် အခြား term အားလုံးကို စုစည်းသည့် ကုန်ကျစရိတ် ဝင်ရိုး ဖြစ်သည် — run တစ်ခုစီသည် model call၊ scorer နှင့် လူသား review သုံးခုလုံးကို တစ်ပြိုင်နက် စားသည်။ ဥပမာ (က) တွင် item ၅၀၀ ရှိသည့် run တစ်ခုသည် judge နှင့်ဆိုလျှင် USD ၅၀.၇၈၃၀ ကုန်ကျပြီး ထို ပမာဏ၏ ၉၈.၅ ရာခိုင်နှုန်းသည် လူသား ပြန်လည်စစ်ဆေးမှု ဖြစ်သည်။ ထို့ကြောင့် eval ကို တိုးချဲ့လျှင် ပထမဆုံး ကန့်သတ်ချက်သည် model token မဟုတ်ဘဲ review အရေအတွက် ဖြစ်သည်။ ထုတ်လုပ်မှု အင်ဂျင်နီယာသည် run အရေအတွက် (commit တိုင်း၊ ညတိုင်း) ကို ဤ USD တန်ဖိုးနှင့် တွဲဖက်၍ အကန့်အသတ် သတ်မှတ်ရမည်၊ မသတ်မှတ်လျှင် eval သည် အသုံးပြုနိုင်ခြင်း မရှိသည့် ကုန်ကျစရိတ် တစ်ခု ဖြစ်လာသည်။

#### Eval Set

Eval Set သည် သတ်မှတ်ထားသည့် စွမ်းရည် သို့မဟုတ် အန္တရာယ်တစ်ခုအတွက် input များ၊ မျှော်လင့်ထားသည့် ဂုဏ်သတ္တိများ၊ scoring rule များနှင့် metadata ကို စုစည်းထားသည့် version စီမံထားသည့် အစု ဖြစ်သည်။ ၎င်းသည် data storage ဝင်ရိုး အပေါ် ရောက်သည် — မေးခွန်း ၅၀၀ ရှိသည့် အစုတစ်ခုသည် run တစ်ခုလျှင် transcript နှင့် judge verdict အပါအဝင် ၂.၄၄ MiB ခန့် သိမ်းရပြီး ထို ပမာဏသည် version အရေအတွက်နှင့် run အရေအတွက်နှင့် တိုက်ရိုက် အချိုးကျ တိုးသည် (ဥပမာ (က))။ ကုန်ကျစရိတ်သည် ချွေတာနိုင်သည့် အပိုင်း ဖြစ်သော်လည်း version မပါဘဲ ရလဒ်ကို မှတ်တမ်းတင်လျှင် ထို ရလဒ်ကို မည်သည့် အစုနှင့် နှိုင်းယှဉ်ခဲ့သည်ကို ပြန်ရှာနိုင်ခြင်း မရှိပါ။ ထုတ်လုပ်မှု အင်ဂျင်နီယာသည် အစု တိုင်းအတွက် version အမည်၊ item အရေအတွက် နှင့် ဖန်တီးသည့် ရက်စွဲကို မှတ်တမ်းတင်ရမည်။

#### Model Card

Model Card သည် ရည်ရွယ်ထားသည့် အသုံးပြုမှုများ၊ evaluation အခြေအနေများ၊ စွမ်းဆောင်ရည် လက္ခဏာများ၊ ကန့်သတ်ချက်များနှင့် ဘေးကင်းရေး စဉ်းစားချက်များကို ဖော်ပြသည့် ဖွဲ့စည်းထားသော အစီရင်ခံစာ ဖြစ်သည်။ ၎င်းသည် data storage ဝင်ရိုး အပေါ် ရောက်သောကြောင့် volume အရ သေးငယ်သည်၊ သို့သော် ရက်စွဲ နှင့် slice အချက်အလက် ပါဝင်မှသာ တန်ဖိုး ရှိသည်။ အထောက်အထား အသစ် တိုင်းအတွက် ရက်စွဲ နှင့် အုပ်စုခွဲ ရလဒ် မပါလျှင် အောက်ပိုင်း တည်ဆောက်သူသည် ထို အထောက်အထားသည် သူ၏ အသုံးပြုသူများအတွက် သက်ဆိုင်ခြင်း ရှိ မရှိ ဆုံးဖြတ်နိုင်ခြင်း မရှိပါ။ ထို့ကြောင့် အင်ဂျင်နီယာသည် model card ကို version တိုင်းနှင့် အတူ သိမ်းဆည်းပြီး အဆို တိုင်း၏ ရက်စွဲကို ဖော်ပြရမည်။

#### Benchmark Contamination

Benchmark Contamination သည် evaluation နမူနာများနှင့် စနစ်ကို ပိုမိုကောင်းမွန်စေရန် အသုံးပြုခဲ့သည့် data အကြား ထပ်နေမှု သို့မဟုတ် အချက်အလက် ယိုစိမ့်မှု ဖြစ်သည်။ ၎င်းသည် data storage ဝင်ရိုး အပေါ် ကုန်ကျစရိတ် တစ်ခု ထည့်သည် — ဇစ်မြစ် ခြေရာခံခြင်း၊ exact နှင့် near-duplicate ရှာဖွေခြင်း နှင့် သီးသန့် test case များ ချန်လှပ်ထားခြင်း တို့သည် သိမ်းဆည်းသည့် အညွှန်း နှင့် compute လိုအပ်သည်။ ရွေ့လျားသည့် ကိန်းသည် overlap အချိုး ဖြစ်ပြီး ၎င်းသည် သုည နှင့် နီးကပ်နေမှသာ benchmark score ကို မမြင်ဖူးသေးသည့် အလုပ် စွမ်းရည် အဖြစ် အသုံးပြုနိုင်သည်။ Contamination ရှိပါက ကျိုးပျက်သည့် အရာသည် score မဟုတ်ဘဲ model ရွေးချယ်မှု ဖြစ်သည် — ပိုမိုကြီးမားသည့် model ကို ထပ်တလဲလဲ ကြုံဖူးမှုကြောင့် ရွေးချယ်မိသည်။

### မိသားစု (ခ) — ရမှတ် တိုင်းတာသည့် metric များ (scored metrics)

#### Exact Match (EM)

Exact Match သည် output ၏ normalized representation သည် လက်ခံထားသည့် အကိုးအကား အဖြေနှင့် အတိအကျ တူညီသည့်အခါတွင်သာ မှန်ကန်သည်ဟု ရေတွက်သည့် metric ဖြစ်သည်။ ၎င်းသည် eval compute and cost ဝင်ရိုးတွင် ချွေတာသည့် ရွေးချယ်မှု ဖြစ်သည် — scoring သည် string နှိုင်းယှဉ်ခြင်း သာ ဖြစ်သည့်အတွက် judge token လုံးဝ မလိုပါ။ ရွေ့လျားသည့် ကိန်းသည် EM rate ဖြစ်ပြီး ၎င်းသည် partial credit ကို လုံးဝ မဖော်ပြသည့်အတွက် အဖြေ မှန်သော်လည်း format ကွာခြားသည့် item များသည် ကျရှုံးသည်ဟု ရေတွက်ခံရသည်။ ထို့ကြောင့် normalization စည်းမျဉ်း နှင့် လက်ခံသည့် အကိုးအကား အားလုံးကို run မတိုင်မီ သတ်မှတ်ပြီး output များစွာ မှန်နိုင်သည့် အလုပ်များတွင် EM ကို အလုပ်နှင့်ဆိုင်သည့် စစ်ဆေးမှုများနှင့် တွဲဖက် အသုံးပြုရမည်။

#### ROUGE

ROUGE သည် n-gram ထပ်တူမှု သို့မဟုတ် longest common subsequence ကဲ့သို့ အစိတ်အပိုင်းများကို အသုံးပြု၍ ဖန်တီးထားသည့် စာသားကို အကိုးအကား စာသားနှင့် နှိုင်းယှဉ်သည့် metric အုပ်စု ဖြစ်သည်။ ၎င်းသည်လည်း eval compute and cost ဝင်ရိုးတွင် ချွေတာသည့် ရွေးချယ်မှု ဖြစ်သည် — model call တစ်ခုမျှ မလိုဘဲ အနှစ်ချုပ် (summary) များကို စျေးနှုန်း သက်သာစွာ နှိုင်းယှဉ်နိုင်သည်။ ရွေ့လျားသည့် ကိန်းသည် ROUGE-1 နှင့် ROUGE-L ၏ F1 ဖြစ်ပြီး ၎င်း၏ အားနည်းချက်သည် မျက်နှာပြင် ထပ်တူမှုသာ တိုင်းတာခြင်း ဖြစ်သည် — အဓိပ္ပာယ် တူညီမှုကို လွတ်သွားနိုင်ပြီး အချက်အလက် အရည်အသွေး မရှိဘဲ အကိုးအကားမှ ကူးချထားသည့် စာသားကို ဆုချနိုင်သည်။ ထို့ကြောင့် ROUGE ကို hallucination စစ်ဆေးမှု သို့မဟုတ် judge score နှင့် တွဲဖက်ရမည်၊ တစ်ခုတည်း အသုံးပြုရမည် မဟုတ်ပါ။

#### Precision & Recall

Precision သည် အမှတ်အသားပြုထားသည့် အရာများထဲမှ မည်မျှ မှန်ကန်သည်ကို မေးပြီး Recall သည် သက်ဆိုင်သည့် အရာများထဲမှ မည်မျှ ရှာတွေ့သည်ကို မေးသည်။ ဤစုံသည် eval compute and cost ဝင်ရိုးအပေါ် ကုန်ကျစရိတ် အရေးပါသည့် အချက်တစ်ခု ထည့်သည် — threshold ပြောင်းတိုင်း ရမှတ် အစုတစ်ခုလုံးကို ပြန်လည် စစ်ရသည်၊ သို့သော် ကိန်း နှစ်ခုကို အတူတကွ ကြည့်ခြင်းသည် ပျမ်းမျှ တိကျမှု တစ်ခုတည်း ကြည့်ခြင်းထက် ဘယ် အမှား အမျိုးအစားကို ခံနိုင်သည်ကို ရှင်းလင်းစေသည်။ ရွေ့လျားသည့် ကိန်းသည် သတ်မှတ်ထားသည့် threshold တစ်ခုရှိ precision၊ recall နှင့် ၎င်းတို့၏ harmonic mean ဖြစ်သည့် F1 ဖြစ်သည်။ ထိန်းချုပ်မှု အလွှာတွင် မှားယွင်းစွာ ပိတ်ခြင်း (precision ကျ) နှင့် လွတ်သွားခြင်း (recall ကျ) အကြား ဆုံးဖြတ်ချက်သည် အမှား တစ်ခုစီ၏ ကုန်ကျစရိတ်အပေါ် မူတည်ရမည်။

#### Pass@k

Pass@k သည် အလုပ်အစုတစ်ခု အတွင်း k အကြိမ် နမူနာယူထားသည့် လျာထားချက်များထဲမှ အနည်းဆုံး တစ်ခုသည် သတ်မှတ်ထားသည့် မှန်ကန်မှု စစ်ဆေးမှုကို အောင်မြင်သည့် အလုပ်များ၏ အချိုးအစား ဖြစ်သည်။ ၎င်းသည် eval compute and cost ဝင်ရိုး တွင် ကိန်း k အတိုင်း တိုက်ရိုက် ကုန်ကျသည် — task တိုင်းအတွက် k ကြိမ် ဖန်တီးရသည့်အတွက် token ပမာဏသည် k ဆ တိုးသည်။ ထို့ကြောင့် Pass@k ၏ score တိုးခြင်းသည် ပထမဆုံး အဖြေ ပိုကောင်းလာခြင်း မဟုတ်ဘဲ attempt budget ကြီးလာခြင်း ဖြစ်နိုင်သည်၊ ဤ ကောက်ချက်ချမှု မှားသည့်အခါ ထုတ်လုပ်မှုတွင် ပထမဆုံး attempt ကို လက်ခံသည့် စနစ်သည် မျှော်လင့်သည့် အရည်အသွေးကို မရရှိပါ။ အင်ဂျင်နီယာသည် sampling configuration နှင့် estimator အသေးစိတ်ကို k နှင့် အတူ အစီရင်ခံရမည်။

#### Calibration

Calibration သည် စနစ်က ဖော်ပြသည့် ယုံကြည်မှုအဆင့် နှင့် ထို confidence အဆင့်ရှိ ခန့်မှန်းချက်များ အမှန်ဖြစ်သည့် လက်တွေ့ အကြိမ်အရေအတွက် အကြား ကိုက်ညီမှု ဖြစ်သည်။ ၎င်းသည် eval compute and cost ဝင်ရိုး တွင် သွယ်ဝိုက်သည့် ကုန်ကျစရိတ် ဖြစ်သည် — calibration ကို တိုင်းတာရန် ခန့်မှန်းချက်များကို confidence အဆင့် အလိုက် အုပ်စုဖွဲ့ရပြီး bin တိုင်းတွင် item အလုံအလောက် ရှိရမည်၊ ထို့ကြောင့် eval set သည် ပိုမို ကြီးရသည်။ ရွေ့လျားသည့် ကိန်းသည် expected calibration error (ECE) ဖြစ်ပြီး ထိုတန်ဖိုး ကြီးလျှင် အခြေအနေကို ကျိုးပျက်စေသည့် အရာသည် ခြုံငုံ တိကျမှု မဟုတ်ဘဲ လူသား မှီခိုသည့် score ဖြစ်သည်။ ကွာဟမှု လက်မခံနိုင်လောက်ပါက recalibrate လုပ်ခြင်း သို့မဟုတ် မသေချာသည့် အခြေအနေတွင် အဖြေပေးခြင်းမှ ရှောင်ကြဉ်ခြင်း ပြုလုပ်ရမည်။

### မိသားစု (ဂ) — အကဲဖြတ်သူ နှင့် အရည်အသွေး (judging and quality)

#### LLM-as-a-Judge

LLM-as-a-Judge သည် ဘာသာစကား model တစ်ခုကို အသုံးပြု၍ အခြား စနစ်တစ်ခု၏ output ကို rubric တစ်ခုနှင့် ဆန့်ကျင်စွာ score ပေးခြင်း၊ နှိုင်းယှဉ်ခြင်း သို့မဟုတ် ဝေဖန်ခြင်း ဖြစ်သည်။ ၎င်းသည် ရှင်းလင်းမှု သို့မဟုတ် ညွှန်ကြားချက် လိုက်နာမှုကဲ့သို့ exact-match test အဖြစ် ဖော်ပြရန် ခက်ခဲသည့် ဂုဏ်သတ္တိများကို scale ချပေးသည်၊ သို့သော် အခြေခံအဆောက်အအုံ အမြင်ဖြင့် ၎င်းသည် cost per eval run ဝင်ရိုး၏ ဒုတိယ အစိတ်အပိုင်း ဖြစ်လာသည်။ ဥပမာ (က) တွင် judge သည် item တစ်ခုလျှင် input token ၁၇၀၀ နှင့် output token ၆၀ စားပြီး ၅၀၀ item အတွက် USD ၀.၂၅၈၀ ကုန်ကျသည် — ထို ပမာဏသည် လူသား review နှင့် နှိုင်းယှဉ်လျှင် ၀.၅ ရာခိုင်နှုန်းသာ ဖြစ်သည့်အတွက် judge ကို တိုးချဲ့ခြင်းသည် ကုန်ကျစရိတ် အကြီးမားဆုံး အချက် မဟုတ်ပါ။ သို့သော် judge score သည် ground truth မဟုတ်သည့်အတွက် အစဉ်လိုက်မှု၊ စကားလုံး များပြားမှု သို့မဟုတ် စတိုင်ကြောင့် bias ဖြစ်နိုင်ပြီး ၎င်း၏ score များကို လူသား ပြန်လည်စစ်ဆေးထားသည့် နမူနာများနှင့် ချိန်ညှိရမည်။

#### Hallucination

Hallucination သည် မှားယွင်းသည့်၊ ရရှိနိုင်သည့် အထောက်အထားဖြင့် ပံ့ပိုးမှု မရှိသည့် သို့မဟုတ် အလုပ်၏ အမှန်တရား အရင်းအမြစ်နှင့် ကိုက်ညီမှု မရှိသည့် ဖန်တီးထုတ်လုပ်သည့် အကြောင်းအရာ ဖြစ်သည်။ ထို ဖော်ပြချက်သည် training data တွင် ပါဝင်ခဲ့ခြင်း ရှိ မရှိကို ပုံမှန်အားဖြင့် စစ်ဆေးနိုင်ခြင်း မရှိသည့်အတွက် ထုတ်လုပ်မှု စစ်ဆေးမှုများသည် ပံ့ပိုးမှု၊ မှန်ကန်မှုနှင့် ခြေရာခံနိုင်မှုတို့ကို အဓိကထားရမည်။ ဤအချက်သည် eval compute and cost ဝင်ရိုးအပေါ် တိုက်ရိုက် သက်ရောက်သည် — claim တိုင်းအတွက် citation နှင့် verifier စစ်ဆေးမှု လိုအပ်သည့်အတွက် အဖြေ တစ်ခုစီ၏ စစ်ဆေးရေး token ပမာဏသည် output token ပမာဏကို ကျော်လွန်နိုင်သည်။ ရွေ့လျားသည့် ကိန်းသည် အထောက်အထား ရရှိသည့် claim အချိုး ဖြစ်ပြီး ထို အချိုး ကျဆင်းလျှင် အသုံးပြုသူထံ အထောက်အထား မရှိသည့် အဆို ရောက်ရှိသည်။

### မိသားစု (ဃ) — ထိန်းချုပ်မှုများ (controls in the request path)

#### Guardrails

Guardrails သည် input များ၊ tool အသုံးပြုမှု၊ output များ၊ permission များနှင့် escalation ကို ကန့်သတ်သည့် စနစ် ထိန်းချုပ်မှုများ ဖြစ်သည်။ ၎င်းတို့တွင် schema များ၊ policy စစ်ဆေးမှုများ၊ classifier များ၊ allowlist များ၊ sandboxing၊ approval များနှင့် လုပ်ဆောင်ပြီးနောက် စစ်ဆေးမှုများ ပါဝင်နိုင်သည်။ အခြေခံအဆောက်အအုံ အမြင်ဖြင့် ၎င်း၏ ကုန်ကျစရိတ်သည် request လမ်းကြောင်း အတွင်းရှိ မီလီစက္ကန့် ဖြစ်သည် — ဥပမာ (ခ) တွင် classification ၁၂၀ ms သည် ၅၀ requests/s၊ 64 worker အခြေအနေတွင် added p50 ကို ၉၀၀ ms မှ ၁၀၂၃.၈၉ ms သို့ တင်ပြီး throughput ကို ၇၁.၁ မှ ၆၂.၇ requests/s သို့ ကျဆင်းစေသည်။ ရွေ့လျားသည့် ကိန်းသည် added p50/p95 latency နှင့် ကျဆင်းသည့် requests/s ဖြစ်ပြီး ထို ကိန်း နှစ်ခုကို တစ်ပြိုင်နက် တွက်ခြင်းသည် မရှိမဖြစ် ဖြစ်သည်၊ မည်သည့် filter တစ်ခုတည်းမှ ကျရှုံးမှု ပုံစံ အားလုံးကို ဖုံးလွှမ်းနိုင်ခြင်း မရှိသည့်အတွက် ထိန်းချုပ်မှုများကို အန္တရာယ်အလိုက် အလွှာလိုက် စီစဉ်ရမည်၊ ထို အလွှာ အရေအတွက်သည် latency နှင့် တိုက်ရိုက် အချိုးကျ တိုးသည်။

#### Prompt Injection

Prompt Injection သည် ယုံကြည်စိတ်ချရခြင်း မရှိသည့် အကြောင်းအရာတစ်ခုက model အား ရည်ရွယ်ထားသည့် ညွှန်ကြားချက်များကို လျစ်လျူရှုစေခြင်း၊ data ကို ဖော်ထုတ်စေခြင်း၊ tool များကို အလွဲသုံးစေခြင်း သို့မဟုတ် အသုံးပြုသူ၏ ပန်းတိုင် အပြင်ဘက် လုပ်ဆောင်ချက်များ လုပ်ဆောင်စေခြင်းတို့ဖြင့် လွှမ်းမိုးသည့် တိုက်ခိုက်မှု သို့မဟုတ် ကျရှုံးမှု ပုံစံ ဖြစ်သည်။ ၎င်းသည် latency of a guardrail in the request path ဝင်ရိုးအပေါ် ရောက်သည် — ဒုတိယ classifier တစ်ခု၊ provenance tag စစ်ဆေးမှုနှင့် အကျိုးသက်ရောက်မှု ရှိသည့် လုပ်ဆောင်ချက်များအတွက် approval စောင့်ချိန် တို့သည် request တိုင်း၏ စုစုပေါင်း အချိန်ကို တိုးစေသည်။ ရွေ့လျားသည့် ကိန်းသည် added ms နှင့် block/allow အချိုး ဖြစ်ပြီး ကျိုးပျက်သည့် အရာသည် model မဟုတ်ဘဲ tool permission နှင့် approval မူဝါဒ ဖြစ်သည်၊ input filtering တစ်ခုတည်းဖြင့် အန္တရာယ်ရှိသည့် ညွှန်ကြားချက် တစ်ခုစီကို တရားဝင် အကြောင်းအရာများနှင့် ယုံကြည်စိတ်ချစွာ ခွဲခြားနိုင်ခြင်း မရှိပါ။

#### Least Privilege

Least Privilege သည် model၊ agent၊ tool သို့မဟုတ် အသုံးပြုသူတစ်ဦးအား လက်ရှိ အလုပ်အတွက် လိုအပ်သည့် permission များကိုသာ၊ ထို permission များ လိုအပ်သည့် ကာလအတွက်သာ ပေးအပ်ခြင်း ဖြစ်သည်။ ၎င်းသည် production consequence ဝင်ရိုး၏ အဓိက ကိန်း ဖြစ်သည် — agent တစ်ခုလျှင် permission နှင့် tool အရေအတွက် နည်းလျှင် ကျရှုံးမှု တစ်ခုက ဖြစ်ပေါ်စေနိုင်သည့် ထိခိုက်မှု နယ်ပယ် ကျဉ်းမြောင်းသည်။ ဤဝင်ရိုးသည် ငွေ မကုန်ကျဘဲ အန္တရာယ် ကို လျှော့ချသည့် တစ်ခုတည်းသော ဝင်ရိုး ဖြစ်သည်၊ အကြောင်းမှာ ၎င်းသည် လုပ်ဆောင်နိုင်သည့် အရာ အရေအတွက်ကို လျှော့ချခြင်း ဖြစပြီး permission အပိုများ ပြင်ဆင်ရန် အချိန် သာ ကုန်ကျသည်။ ထို့ကြောင့် documentation agent တစ်ခုအား source file များအတွက် read access နှင့် branch တစ်ခုအတွက် write access ပေးအပ်သော်လည်း production credential သို့မဟုတ် merge permission ပေးအပ်ခြင်း မပြုရ။

#### Verification Gate

Verification Gate သည် သတ်မှတ်ထားသည့် အထောက်အထားသည် မှန်ကန်မှု သို့မဟုတ် အရည်အသွေး စံနှုန်းတစ်ခုကို ဖြည့်ဆည်းသည်အထိ တိုးတက်မှုကို တားဆီးသည့် ထိန်းချုပ်မှု အမှတ် ဖြစ်သည်။ ၎င်းသည် throughput of continuous evaluation ဝင်ရိုးအပေါ် ရောက်သည် — gate တစ်ခုသည် candidate တိုင်းအတွက် စက္ကန့် အရေအတွက် ကုန်ကျသော်လည်း အထောက်အထား မပြည့်မီ နောက်အဆင့် သို့ မလွှတ်ခြင်းဖြင့် အောက်ပိုင်း လုပ်ငန်း၏ အလဟဿ compute ကို ချွေတာသည်။ ရွေ့လျားသည့် ကိန်းသည် gate အောင်မြင်သည့် အချိုး နှင့် candidate တိုင်း၏ စက္ကန့် ဖြစ်ပြီး ထို ကိန်း နှစ်ခုကို ကြည့်၍ gate ကို ကျယ်လွန်းခြင်း (စောင့်ချိန် ကြီး) နှင့် ကျဉ်းလွန်းခြင်း (အထောက်အထား လွတ်) အကြား ချိန်ညှိရမည်။ ဤ term သည် model ၏ ပြီးစီးပြီဟူသည့် အဆိုကို အထောက်အထား အခြေခံသည့် ဆုံးဖြတ်ချက် အဖြစ် ပြောင်းလဲပေးသည်။

### မိသားစု (င) — ကိုက်ညီမှု နှင့် စောင့်ကြည့်ခြင်း (alignment and monitoring)

#### Alignment

Alignment သည် model သို့မဟုတ် AI စနစ်တစ်ခုကို ရည်ရွယ်သည့် ပန်းတိုင်၊ ကန့်သတ်ချက်နှင့် လူသား၏ ဦးစားပေးချက်များနှင့် ကိုက်ညီသည့် အပြုအမူ ပြသစေရန် ဆောင်ရွက်သည့် လုပ်ငန်းစဉ် ဖြစ်သည်။ ၎င်းသည် production consequence ဝင်ရိုး၏ အထွတ်အထိပ် ဖြစ်သည် — alignment အတွက် evaluation၊ oversight နှင့် စနစ် ထိန်းချုပ်မှုများ လိုအပ်သည့်အတွက် ကုန်ကျစရိတ်သည် adversarial eval run များ၊ လူသား ပြန်လည်စစ်ဆေးမှု နာရီများနှင့် gate များ အပေါ် ရောက်သည်။ ရွေ့လျားသည့် ကိန်းသည် adversarial case အောင်မြင်သည့် အချိုး ဖြစ်ပြီး ထို အချိုး သည် သာမန် eval score နှင့် မတူညီစွာ ပြောင်းလဲနိုင်သည်။ ကျိုးပျက်သည့် အရာသည် ရှင်းလင်းသည် — စနစ်သည် သတ်မှတ်ထားသည့် metric ကို အကောင်းဆုံးဖြစ်စေနေစဉ် အသုံးပြုသူ၏ အမှန်တကယ် ရည်ရွယ်ချက်ကို ချိုးဖောက်နိုင်သည်၊ ထို့ကြောင့် metric တစ်ခုတည်းဖြင့် alignment ကို မတိုင်းတာနိုင်ပါ။

#### Distribution Shift

Distribution Shift သည် စနစ်တစ်ခုကို တည်ဆောက်ရန် သို့မဟုတ် evaluate လုပ်ရန် အသုံးပြုသည့် data distribution နှင့် deploy လုပ်ပြီးနောက် ကြုံတွေ့ရသည့် distribution အကြား ကွာခြားမှု ဖြစ်သည်။ ၎င်းသည် throughput of continuous evaluation ဝင်ရိုးအပေါ် ရောက်သည် — shift ကို ဖော်ထုတ်ရန် window များ အဆက်မပြတ် run ရပြီး window တိုင်း၏ sample အရေအတွက်က ဖော်ထုတ်နိုင်မှုကို ဆုံးဖြတ်သည်။ ဥပမာ window ၂၀၀၊ baseline ၀.၉၂ ရှိသည့် စောင့်ကြည့်မှုတွင် standard error သည် ၀.၀၁၉၂ ဖြစ်သည်၊ ထို့ကြောင့် shift ၀.၀၇ သည် window တစ်ခုတည်းဖြင့် z တန်ဖိုး ၃.၆၅ သို့ ရောက်ပြီး shift ၀.၀၁ သည် window ၃၃ ခုခန့် စုစည်းမှသာ threshold ကို ကျော်သည်။ ကျိုးပျက်သည့် အရာသည် အသုံးပြုသူ အုပ်စု အသစ် သို့မဟုတ် ဘာသာစကား အသစ် တွင် တိတ်ဆိတ်စွာ ကျဆင်းခြင်း ဖြစ်သည်၊ ထို့ကြောင့် မျှော်လင့်ထားသည့် deployment slice များကို သတ်မှတ်ပြီး slice အလိုက် စွမ်းဆောင်ရည် နှင့် input လက္ခဏာများကို စောင့်ကြည့်ရမည်။

## ၄။ လက်တွေ့ တွက်ချက်မှု သုံးခု

ဤအပိုင်းရှိ output အားလုံးသည် အောက်တွင် ဖော်ပြသည့် command များကို တကယ် run ၍ ရရှိသည့် ရလဒ်များ ဖြစ်သည်။ script များသည် standard library သာ အသုံးပြုပြီး deterministic ဖြစ်သည်။

### (က) eval run တစ်ခု၏ token နှင့် ကုန်ကျစရိတ် — item ၁၀၀၊ ၅၀၀၊ ၂၀၀၀

ဖော်မြူလာ — `answer_usd = in_tok/1e6 × 0.50 + out_tok/1e6 × 1.50`၊ `judge_usd = in_tok/1e6 × 0.30 + out_tok/1e6 × 0.10`၊ `human_usd = items × 0.05 × 2.00`။ ယူဆချက် — answer prompt token ၁၂၀၀၊ answer output token ၃၀၀၊ judge rubric token ၂၀၀၊ judge output token ၆၀၊ answer model စျေးနှုန်း USD ၀.၅၀/၁e၆ input နှင့် USD ၁.၅၀/၁e၆ output၊ judge စျေးနှုန်း USD ၀.၃၀/၁e၆ input နှင့် USD ၀.၁၀/၁e၆ output၊ လူသား review ၅ ရာခိုင်နှုန်း USD ၂.၀၀/item၊ storage ၅ KiB/item/run။ စျေးနှုန်း တိုင်းသည် vendor နှင့် model အလိုက် ကွာခြားသည့်အတွက် `တန်ဖိုးသည် အခြေအနေအလိုက် ကွာခြားသည်`။

ရလဒ်က ပြသည့် အဓိက အချက်မှာ token ကုန်ကျစရိတ် သည် item အရေအတွက်နှင့် တိုက်ရိုက် အချိုးကျ တိုးခြင်း ဖြစ်သည်၊ သို့သော် ထို စျေးနှုန်းများ အောက်တွင် စုစုပေါင်း၏ အကြီးမားဆုံး အစိတ်အပိုင်းသည် လူသား ပြန်လည်စစ်ဆေးမှု ဖြစပြီး judge token သည် ၀.၅ ရာခိုင်နှုန်းသာ ဖြစ်သည်။ ထို့ကြောင့် eval ၅၀၀ item ကို run ၄ ကြိမ်/ရက် run လျှင် USD ၂၀၃.၁၃/ရက် ဖြစ်ပြီး ထို ပမာဏကို လျှော့ရန် ဦးစားပေးရမည့် အရာသည် review အရေအတွက် ဖြစ်သည်။

### (ခ) guardrail က request လမ်းကြောင်းတွင် ထည့်သည့် latency နှင့် ကျဆင်းသည့် throughput

ဖော်မြူလာ — `service_ms = model_ms + guardrail_ms`၊ `a = rps × service_ms / 1000`၊ `rho = a / workers`၊ `Wq = C(c,a) × service_ms / (workers × (1 - rho))`၊ `added p50 = guardrail_ms + (Wq_on - Wq_off)`။ ယူဆချက် — rps ၅၀၊ answer model service ၉၀၀ ms၊ guardrail service ၁၂၀ ms၊ worker ၆၄ ခု၊ worker စျေးနှုန်း USD ၀.၄၂/နာရီ၊ queue model M/M/c (Erlang C)။ ဤ တန်ဖိုးများသည် worker အရေအတွက်နှင့် service time အပေါ် မှီခိုသည့်အတွက် `တန်ဖိုးသည် အခြေအနေအလိုက် ကွာခြားသည်`။

### (ဂ) model နှစ်ခုကို ခွဲခြားရန် လိုအပ်သည့် eval size

ဖော်မြူလာ — `se(n) = sqrt(pA(1-pA)/n + pB(1-pB)/n)`၊ `n* = z² × (pA(1-pA) + pB(1-pB)) / delta²`၊ ခွဲခြားသည့် စည်းမျဉ်း — `gap > 1.96 × se(n)`။ ယူဆချက် — model A accuracy ၀.၇၂၊ model B accuracy ၀.၈၀ (delta ၀.၀၈)၊ z = ၁.၉၆၊ power z = ၀.၈၄၊ discordant rate ၀.၁၅၊ ရမှတ်များသည် fixed linear congruential generator မှ ဆင်းသက်လာသည့် deterministic simulation ဖြစ်သည်။

## ၅။ ဤနယ်ပယ်မှ ဆင်းသက်လာသည့် ထုတ်လုပ်မှု ဆုံးဖြတ်ချက် ခြောက်ခု

**၁။ Eval set အရွယ်အစားနှင့် version သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Eval Set၊ Evaluation (Eval)၊ Exact Match (EM)၊ Pass@k။ သက်သေပြသည့် မက်ထရစ် — analytic n*၊ ၁.၉၆ × se နှင့် separation rate။ ဥပမာ (ဂ) အရ delta ၀.၀၈ အတွက် item ၂၁၈ ခု လိုပြီး run တိုင်း ခွဲခြားရန် ၂၀၄၈ ခု လိုသည့်အတွက် eval set ကို n* တစ်ခုတည်းဖြင့် သတ်မှတ်လျှင် ဆုံးဖြတ်ချက် မှားနိုင်သည်။

**၂။ Eval run ကို မည်မျှ ကြိမ် run မည် သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Evaluation (Eval)၊ LLM-as-a-Judge။ သက်သေပြသည့် မက်ထရစ် — cost per eval run၊ USD/ရက် နှင့် USD/၃၀ ရက်။ ဥပမာ (က) အရ item ၅၀၀ ၏ run တစ်ခုသည် USD ၅၀.၇၈၃၀ ဖြစ်သည့်အတွက် commit တိုင်း run ခြင်းသည် release တိုင်း run ခြင်းထက် ကုန်ကျစရိတ် များစွာ ပိုသည်။

**၃။ Judge ကို ထည့်မည် သို့မဟုတ် လူသား review ကို ချဲ့မည် သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — LLM-as-a-Judge၊ Hallucination၊ ROUGE၊ Exact Match (EM)။ သက်သေပြသည့် မက်ထရစ် — judge token per item၊ judge အချိုး နှင့် review နာရီ။ ဥပမာ (က) တွင် judge သည် run ၏ ၀.၅ ရာခိုင်နှုန်းသာ ဖြစ်သည့်အတွက် ကျယ်ပြန့်သည့် judge coverage ကို လူသား review ကို လျှော့ခြင်းဖြင့် ရနိုင်သည်၊ သို့သော် judge score ကို item အရေအတွက် တစ်ခုတွင် လူသား ပြန်လည်စစ်ဆေးထားသည့် နမူနာနှင့် ချိန်ညှိရမည်။

**၄။ Guardrail ကို request လမ်းကြောင်း အတွင်း ထည့်မည် သို့မဟုတ် အလွှာလိုက် စီစဉ်မည် သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Guardrails၊ Prompt Injection၊ Least Privilege။ သက်သေပြသည့် မက်ထရစ် — added p50/p95 ms၊ ကျဆင်းသည့် requests/s နှင့် ထပ်ထည့်ရသည့် worker အရေအတွက်။ ဥပမာ (ခ) အရ classification ၁၂၀ ms သည် throughput ကို ၁၁.၇၆ ရာခိုင်နှုန်း စားသည့်အတွက် guardrail တိုင်းကို လမ်းကြောင်း အတွင်း မထည့်ဘဲ အန္တရာယ် မြင့်သည့် လုပ်ဆောင်ချက်များတွင်သာ ထည့်ရမည်။

**၅။ Drift monitoring ၏ window နှင့် threshold သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Distribution Shift၊ Calibration၊ Model Card။ သက်သေပြသည့် မက်ထရစ် — z တန်ဖိုး၊ ဖော်ထုတ်ရန် လိုသည့် window အရေအတွက် နှင့် false alert ကုန်ကျစရိတ်။ window ၂၀၀၊ threshold ၃.၀ အခြေအနေတွင် window တိုင်း၏ false-alarm rate သည် ၀.၀၀၂၇ ဖြစ်ပြီး window ၁၄၄/ရက် အတွက် အလဟဿ စုံစမ်းစစ်ဆေးမှု ၀.၃၈၈၈ ကြိမ်/ရက် ဖြစ်သည်၊ threshold ကို ၂.၀ သို့ လျှော့လျှင် ထို အရေအတွက်သည် ၆.၅၅ ကြိမ်/ရက် သို့ တိုးသည်။

**၆။ Verification gate နှင့် approval သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Verification Gate၊ Least Privilege၊ Alignment။ သက်သေပြသည့် မက်ထရစ် — gate အောင်မြင်သည့် အချိုး၊ candidate တိုင်း၏ စက္ကန့် နှင့် ပိတ်ထားသည့် လုပ်ဆောင်ချက် အရေအတွက်။ Verification သည် အထောက်အထားသည် စံနှုန်းများနှင့် ကိုက်ညီခြင်း ရှိ မရှိ စစ်ဆေးပြီး Approval သည် အထောက်အထားကို သိရှိပြီးဖြစ်သည့်အခါတွင်ပင် ဆက်လက်လုပ်ဆောင်ရန် အခွင့်အာဏာ ပေးအပ်သည်၊ ထို့ကြောင့် နှစ်ခုကို ခွဲခြား သတ်မှတ်ရမည်။
