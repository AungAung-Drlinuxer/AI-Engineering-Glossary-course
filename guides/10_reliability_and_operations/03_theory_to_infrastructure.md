# 03 — သီအိုရီမှ ထုတ်လုပ်မှု လည်ပတ်မှုသို့ (Theory to Infrastructure)

ဤစာတမ်းသည် နယ်ပယ် ၁၀ ၏ term ၁၇ ခုလုံးကို ထုတ်လုပ်မှု လည်ပတ်မှု (production operations) အမြင်ဖြင့် ပြန်လည် ဖတ်သည်။ နယ်ပယ် ၉ သည် request တစ်ခုကို မည်သို့ အမြန်ဆုံး ပြီးမြောက်စေမည်ကို ဖြေဆိုသည်။ ဤနယ်ပယ် ၁၀ သည် ထို စနစ်ကို ဖိအား လွန်ကဲခြင်း၊ အစိတ်အပိုင်း ချို့ယွင်းခြင်းနှင့် ပြောင်းလဲမှု အန္တရာယ် အောက်တွင် အသုံးပြုသူထံ ကတိပြုထားသည့် ဝန်ဆောင်မှု အဆင့်အတိုင်း ထိန်းသိမ်းစေမည့် ဆုံးဖြတ်ချက်များကို ဖြေဆိုသည်။

term တစ်ခုစီသည် သီအိုရီ အဖြစ်သာ မကျန်ရပါ။ ၎င်းသည် လက်ခံမည့် request အရေအတွက်၊ queue အတွင်း စောင့်နေသည့် အလုပ်ပမာဏ၊ retry ကြောင့် dependency မြင်ရသည့် ဝန်၊ သို့မဟုတ် failover အတွက် ကုန်ကျသည့် နှစ်စဉ် စရိတ် အနက် တစ်ခုခုကို ရွေ့လျားစေသည်။ ရွေ့လျားသည့် ကိန်းဂဏန်း တစ်ခုစီသည် ထုတ်လုပ်မှု အခြေအနေတွင် တုံ့ပြန်ရမည့် ဆုံးဖြတ်ချက် တစ်ခုစီနှင့် တွဲလျက် ရှိသည်။

ဤစာတမ်းရှိ ကိန်းဂဏန်း အားလုံးသည် `guides/10_reliability_and_operations/scripts/` အောက်ရှိ Python script များမှ ရရှိသည့် တန်ဖိုးများ ဖြစ်သည်။ script များသည် standard library သာ အသုံးပြုသည်၊ offline ဖြစ်သည်၊ deterministic ဖြစ်သည်။ ဤစာတမ်းသည် တိုင်းတာမှု (measurement) ရလဒ် များကို ဖော်ပြခြင်း မပြုပါ။ ဖော်ပြသည့် တန်ဖိုး အားလုံးသည် ဖော်မြူလာနှင့် ယူဆချက် (assumption) မှ တွက်ချက်ထားသည့် တန်ဖိုးများ ဖြစ်သည်။ ယူဆချက် တိုင်းကို သက်ဆိုင်ရာ အပိုင်းတွင် ရှင်းလင်းစွာ ဖော်ပြထားသည်။

## ၁။ ဝင်ရိုး ခြောက်ခု၏ ဝေါဟာရ သတ်မှတ်ချက်

နောက်ပိုင်း အပိုင်းများတွင် ဤဝေါဟာရ ခြောက်ခုကို တူညီသည့် အဓိပ္ပာယ်ဖြင့်သာ အသုံးပြုမည် ဖြစ်သည်။

**memory and capacity headroom** — ကန့်သတ်ထားသည့် အရင်းအမြစ် (memory၊ accelerator slot၊ queue နေရာ၊ downstream quota) နှင့် လက်ရှိ ဝန် အကြား ကျန်ရှိသည့် အတိုင်းအတာ ဖြစ်သည်။ headroom မရှိလျှင် utilisation ကိန်းသည် ကောင်းနေသော်လည်း ပထမဆုံး ဝန် ခုန်တက်မှုတွင် စနစ် ကျိုးပျက်သည်၊ ထို့ကြောင့် ဤဝင်ရိုးသည် အမာခံ ကန့်သတ်ချက် ဖြစ်သည်။

**compute and queueing** — worker၊ thread သို့မဟုတ် queue တစ်ခုတွင် စောင့်နေသည့် အလုပ်ပမာဏနှင့် ၎င်းကို ထမ်းဆောင်သည့် စွမ်းရည် အကြား အချိုး ဖြစ်သည်။ queue ကြီးလျှင် memory စားသည်၊ စောင့်ချိန် တိုးသည်၊ ချို့ယွင်းသည့် dependency အပေါ် retry များ ထပ်တိုးလျှင် ဤဝင်ရိုးသည် ချက်ချင်း ပြည့်သည်။

**latency under load** — ဝန် အောက်တွင် request တစ်ခု ကြုံတွေ့ရသည့် စောင့်ချိန် ဖြစ်သည်။ ပျမ်းမျှနှင့် p50 သည် ကောင်းနေနိုင်သည်၊ သို့သော် p95 နှင့် p99 သည် saturation နီးလျှင် ခုန်တက်သည်။ SLO ကို ပျမ်းမျှဖြင့် မသတ်မှတ်ရ၊ percentile ဖြင့် သတ်မှတ်ရသည်။

**effective throughput** — စနစ် ထုတ်လုပ်သည့် အလုပ်ပမာဏ မဟုတ်ဘဲ deadline အတွင်း အသုံးဝင်စွာ ပြီးမြောက်သည့် အလုပ်ပမာဏ ဖြစ်သည်။ deadline ကျော်သွားသည့် request သည် hardware အချိန် စားပြီးသော်လည်း ရလဒ် မဖြစ်သဖြင့် effective throughput သည် ကျဆင်းသည်။

**cost of reliability** — ရရှိနိုင်မှု၊ ချို့ယွင်းမှု ခံနိုင်ရည်နှင့် ပြန်လည် ကောင်းမွန်မှုကို ဝယ်ယူရန် ကုန်ကျသည့် replica၊ shadow ဝန်၊ လည်ပတ်မှု အချိန်နှင့် လူ့ အရင်းအမြစ် ဖြစ်သည်။ ဤဝင်ရိုးသည် အခြား ဝင်ရိုးများနှင့် လဲလှယ်မှု (trade-off) အဖြစ် အမြဲ ပေါ်လာသည်။

**production consequence** — ထို concept ကို လျစ်လျူရှုလျှင် ထုတ်လုပ်မှုတွင် မည်သည့် အရာ ကျိုးပျက်မည်၊ အသုံးပြုသူ မည်သို့ ခံစားရမည်ကို ဆိုလိုသည်။ ဥပမာ readiness probe ကို မထားလျှင် warmup မပြီးသည့် instance ထံ traffic ရောက်၍ ရှောင်လွှဲနိုင်သည့် ချို့ယွင်းမှု ဖြစ်သည်။

## ၂။ Master table — term ၁၇ ခုလုံး

| Term | primary axis | ကုန်ကျခြင်း / ချွေတာခြင်း | ရွေ့လျားသည့် ကိန်း | ထုတ်လုပ်မှု အကျိုးဆက် |
|---|---|---|---|---|
| Admission Control | compute and queueing | လက်ခံမှု မပြုမီ ငြင်းပယ်ခြင်းဖြင့် queue နေရာ ချွေတာသည်၊ ငြင်းပယ်ချက် ကို caller ထံ ပြန်ပို့ရသည် | queue depth ceiling (requests) | ceiling မရှိလျှင် queue ကြီးထွား၍ လက်ခံပြီးသား request အားလုံး deadline ကျော်သည် |
| Availability | effective throughput | replica နှင့် headroom ကုန်ကျသည်၊ user-visible ချို့ယွင်းမှု ချွေတာသည် | အောင်မြင်သည့် interaction အချိုး (%) | process အသက်ရှင်နေသော်လည်း user သည် အသုံးဝင်သည့် request မပြီးမြောက်နိုင်သည် |
| Canary Release | cost of reliability | traffic အချို့သာ ဖော်ထုတ်ခြင်းဖြင့် အန္တရာယ်ကုန်ကျစရိတ် ချွေတာသည် | canary traffic အချိုး (%) | ချို့ယွင်းချက်သည် user အားလုံးထံ မရောက်မီ ဖမ်းမိသည် |
| Deadline Propagation | latency under load | အချိန် ကုန်ဆုံးပြီးသည့် အလုပ်ကို ရပ်တန့်ခြင်းဖြင့် capacity ချွေတာသည်၊ metric နှင့် ရှင်းလင်းချက် ထည့်ရသည် | remaining budget (ms) | timeout သီးခြားစီ ဖြစ်လျှင် အသုံးမဝင်တော့သည့် အလုပ်က capacity ကို စားနေသည် |
| Error Budget | cost of reliability | budget ကျန်လျှင် ပြောင်းလဲမှုအပေါ် သုံးနိုင်သည်၊ ကုန်လျှင် ရပ်ရသည် | allowed failure ratio (1 - SLO) | budget မရှိဘဲ release လုပ်လျှင် ချို့ယွင်းမှု ပို၍ ကြာသည် |
| Graceful Degradation | effective throughput | optional feature၊ freshness သို့မဟုတ် workload ကို ဖြတ်၍ core service ကို ထိန်းသည် | core ဝန်ဆောင်မှု အောင်မြင်မှု အချိုး (%) | partial failure တွင် request တိုင်း ကျရှုံးခြင်းကို ရပ်တန့်သည် |
| Incident Response | production consequence | coordinator၊ အထောက်အထား ထိန်းသိမ်းမှုနှင့် ဆက်သွယ်ရေး အချိန် ကုန်ကျသည် | detection နှင့် containment အချိန် (min) | တာဝန်ခွဲဝေမှု မရှင်းလျှင် ဆုံးရှုံးမှု ကြာပြီး ဖြေရှင်းမှု ကြံဖန်ဖြစ်လာသည် |
| Load Shedding | effective throughput | ရွေးချယ်ထားသည့် ဝန်ကို ငြင်းပယ်၍ လက်ခံပြီးသား ဝန်ကို ကယ်သည် | shed အချိုး (%) | အားလုံးကို ဆက်လက်လက်ခံလျှင် request အားလုံးနီးပါး deadline လွန်သည် |
| Postmortem | cost of reliability | မှတ်တမ်း ရေးသားရန် အချိန် ကုန်ကျသည်၊ ဖြစ်ရပ် ပြန်ဖြစ်မှု လျော့သည် | ဖြစ်ရပ် ပြန်ဖြစ်သည့် အကြိမ်ရေ | အထောက်အထား မမှတ်တမ်းတင်လျှင် တူညီသည့် ချို့ယွင်းမှု ပြန်ဖြစ်သည် |
| Readiness Probe | memory and capacity headroom | traffic မရသေးသည့် instance သည် warmup ပြီးစီးရန် အချိန် ရသည် | ready instance အချိုး (%) | warmup မပြီးမီ traffic ပို့လျှင် ရှောင်လွှဲနိုင်သည့် ချို့ယွင်းမှု ဖြစ်သည် |
| Retry Budget | compute and queueing | retry traffic ကို ကန့်သတ်၍ dependency အပေါ် ဝန် ချွေတာသည် | retry အချိုး (originals ၏ %) | ကန့်သတ်မထားလျှင် စွမ်းရည် အနည်းဆုံး ဖြစ်နေချိန်တွင် ဝန် ဆတိုးသည် |
| Rollback | production consequence | version သတ်မှတ်ထားသည့် artifact များ ထိန်းသိမ်းမှု ကုန်ကျသည်၊ ချို့ယွင်းမှု အချိန် ချွေတာသည် | recovery time (min) | ပြန်လည် ရယူနိုင်မှု မရှိလျှင် ချို့ယွင်းသည့် release ကို ဆက်ထားရသည် |
| Saturation | memory and capacity headroom | queue depth နှင့် memory အသုံးပြုမှု တိုးလာသည် | ကန့်သတ်သည့် အရင်းအမြစ်၏ အသုံးပြုမှု (%) | utilisation လက်ခံနိုင်သည့် အနေအထား ပေါ်နေသော်လည်း useful throughput ကျဆင်းသည် |
| Service Level Indicator (SLI) | latency under load | တိုင်းတာမှု၏ ကုန်ကျစရိတ် သေးငယ်သည်၊ အဓိပ္ပာယ် သတ်မှတ်ရန် အချိန် ကုန်ကျသည် | အောင်မြင်မှု အချိုးအစား သို့မဟုတ် latency percentile | တိုင်းတာမှု အမှတ် မရှင်းလျှင် reliability ဆွေးနွေးမှု လုပ်ဆောင်နိုင်သည့် အဆင့်သို့ မရောက်သည် |
| Service Level Objective (SLO) | production consequence | ပန်းတိုင် မြင့်လျှင် capacity ကုန်ကျသည်၊ release အန္တရာယ် ချွေတာသည် | window အတွင်း target (%) | ပန်းတိုင် မရှိလျှင် capacity၊ monitoring နှင့် release ဆုံးဖြတ်ချက်များ နယ်နိမိတ် မရှိဖြစ်သည် |
| Shadow Traffic | compute and queueing | request မိတ္တူသည် capacity ကို ထပ်တိုး စားသည်၊ ထို အကျိုးအမြတ်သည် production အထောက်အထား ဖြစ်သည် | shadow အချိုး (%) | အကျိုးဆက် သီးခြားမခွဲလျှင် မိတ္တူ request သည် တကယ့် data ကို ပြောင်းလဲသည် |
| Tail Latency | latency under load | နှေးသည့် request ကို ခြေရာခံရှာဖွေခြင်းသည် လည်ပတ်မှု အချိန် ကုန်ကျသည် | p95 နှင့် p99 latency (ms) | ပျမ်းမျှ ကျန်းမာနေသော်လည်း အဓိပ္ပာယ်ရှိသည့် user အုပ်စု ကြာကြာ စောင့်သည် |

## ၃။ term အလိုက် ရှင်းလင်းချက်

term များကို မိသားစု လေးခုဖြင့် စုစည်းထားသည် — (က) ဝန်ပို ထိန်းချုပ်မှု၊ (ခ) ဝန်ဆောင်မှု အဆင့် တိုင်းတာမှု၊ (ဂ) ပြောင်းလဲမှု ထုတ်လွှတ်မှု၊ (ဃ) ချို့ယွင်းမှု တုံ့ပြန်မှု။ ဤအုပ်စုခွဲမှုသည် အပိုင်း ၂ ၏ ဇယားနှင့် တိုက်ရိုက် ကိုက်ညီသည်။

### မိသားစု (က) — ဝန်ပို ထိန်းချုပ်မှု (overload)

#### Admission Control

Admission control သည် request တစ်ခုကို လက်ခံမှု မပြုမီ အဆင့်တွင် လက်ရှိ စွမ်းရည်၊ priority နှင့် policy အောက်တွင် ဝင်ခွင့် ရ/မရ ကို ဆုံးဖြတ်သည့် gate ဖြစ်သည်။ ၎င်းသည် ကန့်သတ်ထားသည့် နယ်နိမိတ် တစ်ခုတွင် ပိုလွန်သည့် အလုပ်ကို ငြင်းပယ်ခြင်းဖြင့် ဝင်ခွင့် ရပြီးသား request များကို queue ကြီးထွားမှုနှင့် timeout cascade မှ ကာကွယ်သည်။ ရွေ့လျားသည့် ကိန်းသည် queue depth ceiling ဖြစ်သည်။ ဥပမာ (က) တွင် queue ကန့်သတ်ချက် 200 ခုဖြင့် utilisation 0.95 အခြေအနေတွင် p95 စောင့်ချိန်သည် ခန့်မှန်းခြေ 3 s ဖြစ်သည်၊ ဆိုလိုသည်မှာ ceiling ကို ကတိပြုထားသည့် p95 နှင့် ချိတ်ဆက်၍ သတ်မှတ်ရမည် ဖြစ်သည်။ လက်တွေ့တွင် request ၏ ကုန်ကျစရိတ်ကို ခန့်မှန်းရမည်၊ tenant စွမ်းရည်ကို စစ်ဆေးရမည်၊ လိုအပ်သည့် budget ကို atomically သိမ်းဆည်းရမည်။ အခြေအနေသည် ယာယီ ဖြစ်ပြီး caller ၏ retry budget က ခွင့်ပြုသည့်အခါမှသာ retry အကြံပြုချက် ပေးရမည်။

#### Load Shedding

Load shedding သည် demand သည် အသုံးဝင်သည့် ရလဒ် ထုတ်လုပ်နိုင်သည့် စွမ်းရည်ထက် ကျော်လွန်သည့်အခါ overload နယ်နိမိတ် တစ်ခု သို့မဟုတ် အတော်များများတွင် ရွေးချယ်ထားသည့် အလုပ်ကို တမင်တကာ ငြင်းပယ်ခြင်း၊ ချပစ်ခြင်း သို့မဟုတ် ပလပ်ဖျက်ခြင်း ဖြစ်သည်။ overload ဖြစ်နေစဉ် request တိုင်းကို ဆက်လက် လက်ခံနေခြင်းသည် queueing ကို တိုးမြင့်စေပြီး request အားလုံးနီးပါးသည် deadline ကို လွန်ဆန်စေကာ ပြန်လည် ကောင်းမွန်ရန် ပို၍ ခက်ခဲစေသည်။ ရွေ့လျားသည့် ကိန်းသည် shed လုပ်သည့် အချိုးဖြစ်ပြီး ၎င်း၏ တန်ဖိုးသည် လက်ခံပြီးသား အလုပ်၏ အောင်မြင်မှုကို ကာကွယ်ရန် ဝယ်ယူသည့် စျေးနှုန်း ဖြစ်သည်။ လက်တွေ့တွင် အကြောင်းအရာ အရှိဆုံး နယ်နိမိတ်တွင် shed လုပ်ရမည်၊ high-priority အလုပ်နှင့် လက်ခံပြီးသား အလုပ်ကို ထိန်းသိမ်းရမည်၊ overload ဖြစ်နေသည့် နယ်ပယ်ကို ဖော်ထုတ်ရမည်။ admission control နှင့် ကွာခြားချက်မှာ load shedding သည် လက်ခံပြီးသား အလုပ်အပေါ်တွင်လည်း သက်ရောက်နိုင်ခြင်း ဖြစ်သည်။

#### Retry Budget

Retry budget သည် မူလ request များနှင့် နှိုင်းယှဉ်သည့် အနေဖြင့် သို့မဟုတ် အချိန် window တစ်ခုအတွင်း ဖော်ပြသည့် retry traffic အပေါ် သတ်မှတ်ထားသည့် ကန့်သတ်ချက် ဖြစ်သည်။ dependency တစ်ခု နှေးကွေးသည့်အခါ သို့မဟုတ် ချို့ယွင်းသည့်အခါ ကန့်သတ်မထားသည့် retry များသည် စနစ်တွင် လွတ်လပ်သည့် စွမ်းရည် အနည်းဆုံး ဖြစ်နေသည့် အချိန်တွင် ဝန် ကို ဆတိုးမြှင့်ပေးသည်။ ရွေ့လျားသည့် ကိန်းသည် retry အချိုးဖြစ်ပြီး ဥပမာ (ခ) တွင် failure rate 0.50 နှင့် retry 3 ကြိမ်အခြေအနေတွင် ဤအချိုးသည် 0.875 ဖြစ်ကာ dependency မြင်ရသည့် ဝန် သည် 200 req/s မှ 375 req/s သို့ တက်သည်။ မူလ request ၏ 10% အထိသာ retry ခွင့်ပြုသည့် budget ဖြင့် ထို ဝန် သည် 220 req/s တွင် ရပ်သည်။ လက်တွေ့တွင် retry များကို ပထမ ကြိုးစားမှုများနှင့် သီးခြား ရေတွက်ရမည်၊ ဝန်ဆောင်မှုနှင့် tenant အလိုက် ကန့်သတ်ရမည်၊ jitter ထည့်ထားသည့် backoff ကို သုံးရမည်၊ idempotent မဟုတ်သည့် ချို့ယွင်းမှုများအတွက် retry လုပ်ခြင်းကို ရပ်ရမည်။

#### Saturation

Saturation သည် ကန့်သတ်ထားသည့် အရင်းအမြစ် သို့မဟုတ် ဝန်ဆောင်မှု တစ်ခုသည် ၎င်း၏ စွမ်းရည်ကို ကုန်ဆုံးသွားသည့် အတိုင်းအတာ ဖြစ်ပြီး ချက်ချင်း မစတင်နိုင်သည့် queue တွင် စောင့်နေသည့် အလုပ်များလည်း ပါဝင်သည်။ memory၊ accelerator slot၊ queue depth သို့မဟုတ် downstream quota တစ်ခုသည် အသုံးဝင်သည့် throughput ကို ကန့်သတ်နေပြီ ဖြစ်နေချိန်တွင် utilisation တစ်ခုတည်းက လက်ခံနိုင်သည့် အနေအထား ပေါ်နေနိုင်သည်။ ရွေ့လျားသည့် ကိန်းသည် ကန့်သတ်သည့် အရင်းအမြစ်၏ အသုံးပြုမှု ရာခိုင်နှုန်းဖြစ်ပြီး ဥပမာ (က) တွင် utilisation သည် 0.70 တွင် SLO အဆင့်ကို စတင် ထိသည်၊ ဆိုလိုသည်မှာ 0.10 သာ headroom ကျန်သည်။ လက်တွေ့တွင် အဓိက အရင်းအမြစ် တစ်ခုချင်းကို ဖော်ထုတ်ရမည်၊ တက်ကြွနေသည့် အလုပ်နှင့် စောင့်နေသည့် အလုပ်ကို တိုင်းတာရမည်၊ saturation ကို tail latency နှင့် error များနှင့် ဆက်စပ်ရမည်။

### မိသားစု (ခ) — ဝန်ဆောင်မှု အဆင့် တိုင်းတာမှု (service level)

#### Service Level Indicator (SLI)

SLI သည် သတ်မှတ်ထားသည့် အသုံးပြုသူနှင့် သက်ဆိုင်သည့် နယ်နိမိတ်တွင် ဝန်ဆောင်မှု အပြုအမူကို တိုင်းတာသည့် အရေအတွက် အတိုင်းအတာ ဖြစ်သည် — ဥပမာ အောင်မြင်သည့် request အချိုးအစား သို့မဟုတ် သတ်မှတ်ချက် အဆင့်အောက် ရှိသည့် latency ဖြစ်သည်။ reliability ဆွေးနွေးမှုများသည် လေ့လာတွေ့ရှိသည့် အပြုအမူ၊ အကျုံးဝင်သည့် ဖြစ်ရပ်များနှင့် တိုင်းတာမှု အမှတ်တို့ ရှင်းလင်းသည့်အခါမှသာ လုပ်ဆောင်နိုင်သည့် အဆင့်သို့ ရောက်သည်။ ဤနေရာတွင် SLI သည် တိုင်းတာမှု ဖြစ်ပြီး SLO သည် ထို တိုင်းတာမှုအပေါ် ကျင့်သုံးသည့် ပန်းတိုင် ဖြစ်သည် — နှစ်ခုသည် တူညီသည့် အရာ မဟုတ်ပါ။ လက်တွေ့တွင် numerator၊ denominator၊ ဖယ်ထားသည့် အခြေအနေများ၊ data အရင်းအမြစ်နှင့် aggregation window ကို သတ်မှတ်ရမည်၊ ထို့နောက် indicator သည် အသုံးပြုသူများ တကယ် ကြုံတွေ့သည့် ရလဒ်ကို ခြေရာခံကြောင်း အတည်ပြုရမည်။

#### Service Level Objective (SLO)

SLO သည် သတ်မှတ်ထားသည့် လူအုပ်စု (population) နှင့် တိုင်းတာမှု window တစ်ခုအတွင်း SLI တစ်ခုအတွက် သတ်မှတ်ထားသည့် ပန်းတိုင် အတိုင်းအတာ သို့မဟုတ် သတ်မှတ်ချက် အဆင့် ဖြစ်သည်။ ၎င်းသည် မျှော်လင့်ထားသည့် အသုံးပြုသူ ရလဒ်ကို စောင့်ကြည့်မှု၊ စွမ်းရည်၊ release အန္တရာယ်နှင့် incident ဆုံးဖြတ်ချက်များအတွက် လည်ပတ်မှု နယ်နိမိတ် တစ်ခုအဖြစ် ပြောင်းလဲပေးသည်။ SLO သည် အတွင်းပိုင်း reliability ပန်းတိုင် ဖြစ်ပြီး စာချုပ်အခြေခံ သဘောတူညီချက်တွင် လျော်ကြေးများ ပါဝင်နိုင်သဖြင့် အဓိပ္ပာယ်ဖွင့်ဆိုချင်း ကွာခြားနိုင်သည်။ ရွေ့လျားသည့် ကိန်းသည် window အတွင်း target ရာခိုင်နှုန်း ဖြစ်ပြီး ဥပမာ (ဂ) တွင် 99.9% သည် 30 ရက် window ၌ ကျရှုံးခွင့်ပြုသည့် request 30,000 ခုကို အဓိပ္ပာယ်ဖွင့်သည်။ လက်တွေ့တွင် အသုံးပြုသူများ ဂရုစိုက်သည့် indicator ကို ရွေးရမည်၊ လက်ရှိ စွမ်းဆောင်ရည်အစား ထုတ်ကုန် လိုအပ်ချက်များမှ ပန်းတိုင်ကို သတ်မှတ်ရမည်၊ error-budget policy တစ်ခုကို ချိတ်ဆက်ရမည်။

#### Error Budget

Error budget သည် SLO က သတ်မှတ်ထားသည့် တိုင်းတာမှု window အတွင်းတွင် ထို ပန်းတိုင် မကုန်ဆုံးမီ အလုပ်မအောင်မြင်သည့် ဝန်ဆောင်မှုမည်မျှကို ခွင့်ပြုသည်ကို ဖော်ပြသည့် ပမာဏ ဖြစ်သည်။ ၎င်းသည် reliability အလုပ်နှင့် ထုတ်ကုန် အလုပ်အတွက် မျှဝေသည့် ဆုံးဖြတ်ချက် နယ်နိမိတ် တစ်ခုကို ပေးသည် — အသုံးပြုသူ မြင်တွေ့နိုင်သည့် ချို့ယွင်းမှုက ထို budget ကို စားသုံးနေချိန်တွင် အန္တရာယ်ကို နှေးစေရမည် ဖြစ်ပြီး ကျန်ရှိသည့် budget ကို ပြောင်းလဲမှုအပေါ် သုံးနိုင်သည်။ error budget သည် incident များ ဖြစ်ပေါ်စေရန် ခွဲတမ်း မဟုတ်ပါ၊ ၎င်းသည် အသုံးပြုသူထံ အခြေပြုသည့် reliability ပန်းတိုင်မှ ဆင်းသက်လာသည့် လည်ပတ်မှု policy ဖြစ်သည်။ ရွေ့လျားသည့် ကိန်းသည် allowed failure ratio (1 - SLO) ဖြစ်ပြီး ဥပမာ (ဂ) တွင် ထို အချိုးသည် 0.001000 ဖြစ်ကာ burn rate 2.0x တွင် budget သည် 15.00 ရက်အတွင်း ကုန်ဆုံးသည်။ လက်တွေ့တွင် budget ကို SLO မှ ဆင်းသက်ရမည်၊ အကြောင်းရင်းနှင့် အသုံးပြုသူ အုပ်စု အလိုက် burn ကို ခြေရာခံရမည်၊ ကုန်ဆုံးမီ release လုပ်ဆောင်ချက်များကို သတ်မှတ်ရမည်။

#### Availability

Availability သည် သတ်မှတ်ထားသည့် တိုင်းတာမှု နယ်နိမိတ် တစ်ခုအောက်တွင် အသုံးပြုသူများသည် သတ်မှတ်ထားသည့် လက်ခံနိုင်သည့် ဝန်ဆောင်မှုကို ရရှိနိုင်သည့် အကျုံးဝင်သည့် ဝန်ဆောင်မှု အပြန်အလှန် ဆက်သွယ်မှုများ သို့မဟုတ် အချိန် ကာလများ၏ အချိုးအစား ဖြစ်သည်။ ဝန်ဆောင်မှု process လည်ပတ်နေသော်လည်း အသုံးပြုသူများသည် အသုံးဝင်သည့် request များကို မပြီးမြောက်နိုင်သေးသည့် အခြေအနေ ရှိနိုင်သဖြင့် availability ကို process uptime တစ်ခုတည်းနှင့် မချိတ်ဆက်ဘဲ အသုံးပြုသူ မြင်တွေ့နိုင်သည့် အောင်မြင်မှုနှင့် ချိတ်ဆက်ရမည်။ ၎င်းသည် reliability ရလဒ် တစ်ခု ဖြစ်ပြီး latency၊ correctness၊ safety သို့မဟုတ် အသုံးပြုသူ အုပ်စု တိုင်း၏ အတွေ့အကြုံကို ဖော်ပြသည် မဟုတ်ပါ။ ရွေ့လျားသည့် ကိန်းသည် အောင်မြင်သည့် interaction အချိုးအစား ဖြစ်ပြီး ဥပမာ (ဂ) တွင် no redundancy အခြေအနေသည် တစ်နှစ်လျှင် downtime 8.00 နာရီ ဖြစ်သည်။ လက်တွေ့တွင် အကျုံးဝင်သည့် ဖြစ်ရပ်များနှင့် လက်ခံနိုင်သည့် ရလဒ်များကို သတ်မှတ်ရမည်၊ မှတ်တမ်းတင်ထားသည့် အခြေအနေများကိုသာ ဖယ်ထားရမည်၊ စုစုပေါင်း ချို့ယွင်းမှုများနှင့် ကြာရှည်သည့် တစ်စိတ်တစ်ပိုင်း ယုတ်လျော့မှု နှစ်ခုလုံးကို စစ်ဆေးရမည်။

#### Tail Latency

Tail latency သည် အနှေးဆုံး request အစိတ်အပိုင်း ကြုံတွေ့ရသည့် latency ဖြစ်ပြီး သတ်မှတ်ထားသည့် workload နှင့် အချိန် window တစ်ခုအောက်တွင် မြင့်မားသည့် percentile တစ်ခုဖြင့် အများအားဖြင့် အနှစ်ချုပ် ဖော်ပြသည်။ queueing၊ contention၊ retry သို့မဟုတ် ကွဲပြားသည့် request ကုန်ကျစရိတ်တို့ကြောင့် အဓိပ္ပာယ် ရှိသည့် အသုံးပြုသူ အုပ်စုတစ်ခုသည် ပို၍ ကြာကြာ စောင့်နေချိန်တွင် ပျမ်းမျှများသည် ကျန်းမာနေသည့်ဟု ပေါ်နေနိုင်သည်။ tail latency သည် အနှေးဆုံး request တစ်ခုတည်း မဟုတ်သလို percentile၊ လူအုပ်စု နှင့် တိုင်းတာမှု နယ်နိမိတ် မပါဘဲ အဓိပ္ပာယ် မရှိပါ။ ရွေ့လျားသည့် ကိန်းသည် p95 နှင့် p99 ဖြစ်ပြီး ဥပမာ (က) တွင် utilisation 0.60 ၏ p50 သည် 23.60 ms ဖြစ်သော်လည်း p95 သည် 310.42 ms ဖြစ်သည်၊ ဆိုလိုသည်မှာ p95/p50 အချိုး 13.15x ဖြစ်သည်။ လက်တွေ့တွင် route နှင့် workload အလိုက် percentile အတော်များများကို ဖော်ပြရမည်၊ timeout များကို censored သို့မဟုတ် မအောင်မြင်သည့် လေ့လာတွေ့ရှိချက်များအဖြစ် ထားရှိရမည်၊ နှေးကွေးသည့် request များကို dependency များတစ်လျှောက် ခြေရာခံရမည်။

### မိသားစု (ဂ) — ပြောင်းလဲမှု ထုတ်လွှတ်မှု (change)

#### Canary Release

Canary release သည် rollout ကို ချဲ့ထွင်မည့် အရှေ့တွင် version အသစ်တစ်ခုကို traffic သို့မဟုတ် infrastructure ၏ ကန့်သတ်ထားသည့် အစိတ်အပိုင်း တစ်ခုသို့သာ ဖော်ထုတ်ပေးသည့် deployment နည်းဗျူဟာ ဖြစ်သည်။ ၎င်းသည် ချို့ယွင်းချက်များ၏ သက်ရောက်မှုကို ကန့်သတ်ပေးပြီး ဝန်ဆောင်မှု အသစ်သည် အသုံးပြုသူ အားလုံးထံ မရောက်မီ ထုတ်လုပ်မှု အထောက်အထား ကို ပေးသည်။ ဤနေရာတွင် ရွေ့လျားသည့် ကိန်းသည် canary traffic အချိုး ဖြစ်ပြီး ၎င်းသည် အန္တရာယ် ကုန်ကျစရိတ်နှင့် ပြောင်းပြန် အချိုးကျသည်။ canary release သည် ဖော်ထုတ်မှုကို ကန့်သတ်သည်၊ deployment မလုပ်မီ စမ်းသပ်မှု၊ အတည်ပြုချက် သို့မဟုတ် rollback ပြင်ဆင်မှုတို့ကို အစားထိုးသည် မဟုတ်ပါ။ လက်တွေ့တွင် အကျုံးဝင်သည့် အုပ်စု ငယ်တစ်ခုကို release ထံသို့ route လုပ်ရမည်၊ အရည်အသွေးနှင့် လည်ပတ်မှု metric များကို control နှင့် နှိုင်းယှဉ်ရမည်၊ ကြိုတင် သတ်မှတ်ထားသည့် ချို့ယွင်းချက်များ ပေါ်ပေါက်ပါက ရပ်တန့်ရမည် သို့မဟုတ် rollback လုပ်ရမည်။

#### Shadow Traffic

Shadow traffic သည် လက်ရှိ request traffic ၏ မိတ္တူကို လေ့လာမှုအတွက် ကိုယ်စားလှယ် စနစ်တစ်ခုထံ ပို့လွှတ်ခြင်း ဖြစ်ပြီး ကိုယ်စားလှယ်၏ တုံ့ပြန်မှုသည် အဓိက အသုံးပြုသူ တုံ့ပြန်မှု လမ်းကြောင်း၏ အပြင်တွင် ရှိနေသည်။ မိတ္တူ request သည် အမှန်တကယ် လည်ပတ်နေသေးသဖြင့် ၎င်း၏ အကျိုးဆက်များကို သီးခြားခွဲထားရမည်။ ၎င်းသည် ကိုယ်စားလှယ်ကို တကယ့် input ပုံစံများနှင့် ဝန် အောက်တွင် ဖော်ထုတ်ပေးပြီး အသုံးပြုသူ အပေါ် သက်ရောက်မှုကို ကန့်သတ်ထားသည်။ ရွေ့လျားသည့် ကိန်းသည် shadow အချိုး ဖြစ်ပြီး မိတ္တူ ဝန် အားလုံးသည် compute and queueing ဝင်ရိုးအပေါ် တိုက်ရိုက် ကုန်ကျသည်။ shadow ဝန် သည် အသုံးပြုသူ traffic နှင့် အပြိုင်အဆိုင် မဖြစ်စေရန် တားဆီးရမည်။ canary release နှင့် ကွာခြားချက်မှာ canary သည် တကယ့် အသုံးပြုသူများကို version အသစ်မှ ဝန်ဆောင်ပေးခြင်း ဖြစ်သည်။

#### Rollback

Rollback သည် လက်ရှိ release သည် လည်ပတ်မှု၊ အရည်အသွေး သို့မဟုတ် safety သတ်မှတ်ချက်များကို ချိုးဖောက်သည့်အခါ ယခင် သိရှိပြီးသား deployment သို့မဟုတ် configuration ကို ပြန်လည် ရယူခြင်း ဖြစ်သည်။ agent နှင့် model ပြောင်းလဲမှုများသည် deployment မလုပ်မီ အကဲဖြတ်မှု ရှိသည့်တိုင် ထုတ်လုပ်မှုတွင် ချို့ယွင်းနိုင်သဖြင့် ပြန်လည် ကောင်းမွန်စေမှုကို rollout မလုပ်မီ ကြိုတင် ရေးဆွဲရမည်။ ရွေ့လျားသည့် ကိန်းသည် recovery time ဖြစ်ပြီး ၎င်းသည် ချို့ယွင်းမှုကြောင့် ဆုံးရှုံးသည့် နာရီအရေအတွက်ကို တိုက်ရိုက် ဆုံးဖြတ်သည်၊ ဥပမာ (ဂ) တွင် downtime တစ်နာရီလျှင် ဆုံးရှုံးမှု USD 5000 ဖြစ်သည်။ code rollback သည် database migration၊ ပြင်ပ အကျိုးဆက်၊ cache ထုတ်ထားသည့် ရလဒ်များ သို့မဟုတ် ချို့ယွင်းသည့် release က ရေးထားသည့် data များကို အလိုအလျောက် ပြန်လှန်ပေးသည် မဟုတ်ပါ။ လက်တွေ့တွင် version သတ်မှတ်ထားသည့် artifact များနှင့် configuration ကို ထိန်းသိမ်းရမည်၊ rollback trigger များကို သတ်မှတ်ရမည်၊ command နှင့် data အကျိုးသက်ရောက်မှုများကို လေ့ကျင့် စမ်းသပ်ရမည်။

#### Readiness Probe

Readiness probe သည် ဝန်ဆောင်မှု instance တစ်ခုသည် လက်ရှိတွင် request များကို လက်ခံနိုင်သလား မလက်ခံနိုင်သလားကို traffic လမ်းကြောင်း ချထားသည့် အလွှာထံ ပြောပြသည့် ရောဂါ စစ်ဆေးချက် ဖြစ်သည်။ process တစ်ခု အသက်ရှင်နေသော်လည်း ၎င်း၏ model unload ဖြစ်နေခြင်း၊ dependency များ မရရှိနိုင်ခြင်း သို့မဟုတ် warmup မပြီးစီးခြင်း ဖြစ်နိုင်သဖြင့် traffic ကို စောလွန်းစွာ ပို့လွှတ်ခြင်းသည် ရှောင်လွှဲနိုင်သည့် ချို့ယွင်းမှုများကို ဖြစ်ပေါ်စေသည်။ ၎င်းသည် memory and capacity headroom ဝင်ရိုးအပေါ် သက်ရောက်သည် — cold instance တစ်ခုသည် capacity အဖြစ် မရေတွက်ရသေးပါ။ readiness သည် traffic ရရှိခွင့်ကို ထိန်းချုပ်ပြီး liveness သည် process ကို restart လုပ်သင့်/မသင့် ဆုံးဖြတ်သည်၊ နှစ်ခုစလုံးသည် model တုံ့ပြန်မှု တိုင်း မှန်ကန်မည်ဟု သက်သေမပြပါ။ လက်တွေ့တွင် ဝန်ဆောင်မှု ပေးရန် လိုအပ်သည့် အနည်းဆုံး dependency များကို စစ်ဆေးရမည်၊ startup နှင့် draining အချိန်များတွင် readiness ကို မအောင်မြင်စေရမည်၊ readiness false ဖြစ်ခြင်းကြောင့်သာ process ကို restart လုပ်ခြင်း မပြုရ။

### မိသားစု (ဃ) — ချို့ယွင်းမှု တုံ့ပြန်မှု (incident)

#### Incident Response

Incident response သည် ဝန်ဆောင်မှု၊ data၊ safety သို့မဟုတ် security ကို ခြိမ်းခြောက်သည့် ဖြစ်ရပ်တစ်ခုကို ဖော်ထုတ်ခြင်း၊ ခွဲခြမ်းစိတ်ဖြာခြင်း၊ ထိန်းချုပ်ခြင်း၊ ပြန်လည် ကောင်းမွန်စေခြင်း၊ ဆက်သွယ် အသိပေးခြင်းနှင့် သင်ယူခြင်းတို့ကို ညှိနှိုင်းစွာ လုပ်ဆောင်သည့် လုပ်ငန်းစဉ် ဖြစ်သည်။ incident ဖြစ်နေစဉ်တွင် ရှင်းလင်းသည့် တာဝန်ခွဲဝေမှုနှင့် အထောက်အထားသည် ကြံဖန် ဖြေရှင်းမှုထက် ပို၍ အရေးပါသည်၊ အထူးသဖြင့် model အပြုအမူနှင့် ဖြန့်ကျက်ထားသည့် dependency များက ချို့ယွင်းနေသည့် နယ်နိမိတ်ကို ဖုံးကွယ်သည့်အခါ ဖြစ်သည်။ ရွေ့လျားသည့် ကိန်းသည် detection နှင့် containment အချိန် ဖြစ်ပြီး ထို အချိန်သည် ဆုံးရှုံးမှု၏ အတိုင်းအတာကို ဆုံးဖြတ်သည်။ incident response သည် ဖြစ်ရပ်နှင့် ၎င်း၏ အကျိုးဆက်များကို စီမံပြီး root-cause analysis နှင့် ရေရှည် ကာကွယ်မှုသည် ချက်ချင်း ဝန်ဆောင်မှု ပြန်လည် ရရှိပြီးမှ ဆက်လက် လုပ်ဆောင်ရသည်။ လက်တွေ့တွင် severity နှင့် command တာဝန်များကို သတ်မှတ်ရမည်၊ trace များနှင့် audit မှတ်တမ်းများကို ထိန်းသိမ်းရမည်၊ အန္တရာယ်ရှိသည့် လုပ်ဆောင်ချက်များကို ရပ်တန့်ရမည်၊ ပြုပြင်ရေး အလုပ်များကို အပြီးသတ် လိုက်ပါ ဆောင်ရွက်ရမည်။

#### Postmortem

Postmortem သည် သက်ရောက်မှု၊ ဖော်ထုတ်မှု၊ တုံ့ပြန်မှု၊ အထောက်အကူပြု အခြေအနေများ၊ ပြန်လည် ကောင်းမွန်မှုနှင့် ပိုင်ရှင် သတ်မှတ်ထားသည့် နောက်ဆက်တွဲ လုပ်ဆောင်ချက်များကို ရှင်းလင်းပြီး ခွဲခြမ်းစိတ်ဖြာမှုအစား လူတစ်ဦးကို အပြစ်တင်ခြင်းကို အစားမထိုးသည့် ရေရှည် တည်တံ့သည့် incident မှတ်တမ်း ဖြစ်သည်။ ဖြေရှင်းပြီးသား ပြတ်တောက်မှုတစ်ခုသည် အထောက်အထား အဖြစ် တန်ဖိုး ရှိနေသေးသည်၊ စနစ်၏ အခြေအနေများနှင့် ဆုံးဖြတ်ချက်များကို မှတ်တမ်းတင်ခြင်းသည် ဖြစ်ရပ် တစ်ခုကို ပြန်ဖြစ်မှု လျှော့ချပြီး တုံ့ပြန်ချိန် တိုစေသည့် တိုးတက်မှုများအဖြစ် ပြောင်းလဲပေးသည်။ ၎င်းသည် cost of reliability ဝင်ရိုးအပေါ် ရေရှည် ချွေတာမှု ဖြစ်သည် — မှတ်တမ်းတစ်ခု၏ တန်ဖိုးသည် နောက်ဖြစ်ရပ် တစ်ခု၏ ဆုံးရှုံးမှုကို လျှော့ချမှုဖြင့် တိုင်းသည်။ လက်တွေ့တွင် timeline ကို trace များနှင့် log များမှ တည်ဆောက်ရမည်၊ အစပြုသည့် ဖြစ်ရပ်များနှင့် အထောက်အကူပြု အခြေအနေများကို ခွဲခြားရမည်၊ ရက်စွဲ ပါသည့် လုပ်ဆောင်ချက်များကို တာဝန်ပေးရမည်။

#### Deadline Propagation

Deadline propagation သည် မူလ request သည် အသုံးဝင်စွာ မည်မျှ ကြာကြာ စောင့်နိုင်သေးသည်ကို dependency တစ်ခုချင်းက သိရှိစေရန် ကျန်ရှိသည့် end-to-end အချိန် budget ကို downstream ခေါ်ဆိုမှုများထံ ပေးပို့ခြင်း ဖြစ်သည်။ သီးခြားချင်း သတ်မှတ်ထားသည့် timeout များသည် အသုံးပြုသူ၏ deadline ကို ကျော်လွန်နိုင်ပြီး ရလဒ်သည် အသုံးဝင်တော့မည် မဟုတ်သည့်တိုင် စွန့်ပစ်ထားသည့် အလုပ်များက စွမ်းရည်ကို စားသုံးနေစေသည်။ ထို့ကြောင့် ဤ term သည် effective throughput ဝင်ရိုးအပေါ် တိုက်ရိုက် သက်ရောက်သည် — deadline ကို မပေးပို့လျှင် capacity ၏ တစ်စိတ်တစ်ပိုင်းသည် အသုံးမဝင်တော့သည့် အလုပ်အပေါ် ကုန်ဆုံးသည်။ deadline သည် အကြွင်းမဲ့ သို့မဟုတ် ကျန်ရှိသည့် ပြီးစီးမှု နယ်နိမိတ် ဖြစ်ပြီး retry delay သည် ထို budget တစ်ခုတည်းအတွင်းတွင် ပါဝင်ရမည်။ လက်တွေ့တွင် ingress တွင် request deadline တစ်ခုတည်း သတ်မှတ်ရမည်၊ downstream ခေါ်ဆိုမှု တစ်ခုချင်းအတွက် ကုန်ဆုံးသွားသည့် အချိန်ကို နုတ်ရမည်၊ သက်တမ်း ကုန်ဆုံးသွားသည့် အလုပ်ကို ပလပ်ဖျက်ရမည်။

#### Graceful Degradation

Graceful degradation သည် စွမ်းရည် သို့မဟုတ် dependency များ ချို့ယွင်းသည့်အခါ request တိုင်းကို ချို့ယွင်းစေမည့်အစား ရွေးချယ်နိုင်သည့် အရည်အသွေး၊ feature၊ freshness သို့မဟုတ် workload တို့ကို လျှော့ချ၍ ကန့်သတ်ထားသည့် အဓိက ဝန်ဆောင်မှုကို ထိန်းသိမ်းခြင်း ဖြစ်သည်။ AI စနစ်များသည် နှေးကွေးသည့် သို့မဟုတ် ချို့ယွင်းနိုင်သည့် အစိတ်အပိုင်း အတော်များများအပေါ် မှီခိုလေ့ ရှိသဖြင့် တိကျစွာ သတ်မှတ်ထားသည့် လျှော့ချ mode တစ်ခုသည် တစ်စိတ်တစ်ပိုင်း ချို့ယွင်းချိန်တွင် အဓိက အသုံးပြုသူ ရလဒ်များကို ကာကွယ်နိုင်သည်။ ၎င်းသည် effective throughput ကို ထိန်းသည့် တိုက်ရိုက် လုပ်ဆောင်ချက် ဖြစ်သည် — ဥပမာ (ခ) တွင် retry ကို ကန့်သတ်ခြင်းနှင့် breaker ပွင့်ခြင်းသည် ကျန်ရှိသည့် capacity ကို core အလုပ်အတွက် ချန်ထားသည့် လျှော့ချ mode ဖြစ်သည်။ လျှော့ချ mode သည် ရလဒ် သို့မဟုတ် ဝန်ဆောင်မှု ကတိကို သိသိသာသာ ပြောင်းလဲသည့်အခါ အသုံးပြုသူများကို အသိပေးရမည်၊ လည်ပတ်မှု ရှုထောင့်မှ မြင်တွေ့နိုင်မှု အမြဲ လိုအပ်သည်။ လက်တွေ့တွင် မည်သည့် စွမ်းဆောင်ရည်များကို ပိတ်နိုင်သည်ကို ကြိုတင် သတ်မှတ်ရမည်၊ safety စစ်ဆေးမှုများကို ကာကွယ်ရမည်၊ dependency ချို့ယွင်းမှုအောက်တွင် fallback ကို စမ်းသပ်ရမည်။

### (ခ) retry amplification — ချို့ယွင်းနေသည့် dependency မြင်ရသည့် ဝန်

ဖော်မြူလာ — attempt အရေအတွက် စုစုပေါင်း `1 + f + f^2 + ... + f^r`၊ ဤနေရာတွင် `f` သည် per-attempt failure rate၊ `r` သည် retry အရေအတွက် ဖြစ်သည်။ jitter ၏ သက်ရောက်မှုကို failure wave တစ်ခု၏ retry များကို 10 ms bucket များအဖြစ် ခွဲ၍ တိုင်းသည်။ ယူဆချက် — original demand 200 req/s၊ per-attempt failure rate 0.50၊ retry 3 ကြိမ်၊ backoff 200 ms မှ exponential ဖြစ်သည်၊ retry budget 10%၊ breaker သည် 1 s ပိတ်ထားသည့်အခါ closed fraction 0.500၊ failure wave တစ်ခုသည် 1.0 s ကြာသည်။ ရလဒ် — amplification 1.875x (375.00 req/s)၊ budget ဖြင့် 1.100x (220.00 req/s)၊ breaker ဖြင့် 1.438x (287.50 req/s)။ jitter သည် retry အရေအတွက် 350 ကို မပြောင်းလဲဘဲ peak ကို 20000.00 req/s မှ 2200.00 req/s သို့ လျှော့ချသည်။

ဤရလဒ်က ပြသည့် အဓိက အချက်မှာ replica တစ်ခု ထပ်ထည့်ခြင်း၏ ကုန်ကျစရိတ် (USD 9600/နှစ်) သည် outage 1.92 နာရီ နှင့် ညီမျှသည်၊ ဆိုလိုသည်မှာ တစ်နှစ်လျှင် outage နှစ်နာရီကျော် ဖြစ်သည့် စနစ်များတွင် failover အတွက် replica ထားခြင်းသည် စီးပွားရေး အရ မှန်ကန်သည်။ hot standby + AZ ကဲ့သို့ အလွန်အကျွံ redundancy သည် ကုန်ကျစရိတ် တိုးစေသော်လည်း downtime ကို ထပ်၍ မလျှော့ချနိုင်သည့် အခြေအနေများ ရှိသည်။

## ၅။ ဤနယ်ပယ်မှ ဆင်းသက်လာသည့် ထုတ်လုပ်မှု ဆုံးဖြတ်ချက် ခြောက်ခု

**၁။ Admission control policy သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Admission Control၊ Saturation၊ Load Shedding။ သက်သေပြသည့် မက်ထရစ် — queue depth ceiling နှင့် shed အချိုး။ ဥပမာ (က) အရ queue ကန့်သတ်ချက် 200 ဖြင့် utilisation 0.95 တွင် p95 သည် ခန့်မှန်းခြေ 3 s ဖြစ်သည်၊ ထို့ကြောင့် ceiling ကို ကတိပြုထားသည့် p95 target မှ လှန်တွက်ရမည်။

**၂။ Capacity headroom policy သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Saturation၊ Readiness Probe၊ Availability၊ Tail Latency။ သက်သေပြသည့် မက်ထရစ် — utilisation ceiling နှင့် p95 queue wait။ ဥပမာ (က) တွင် demand 12.00 req/s သည် utilisation 0.60 ဖြစ်ပြီး SLO ceiling 0.70 အောက်တွင် ကျန်ရှိသည့် နေရာ 0.10 သာ ရှိသည်။

**၃။ Retry policy သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Retry Budget၊ Deadline Propagation၊ Tail Latency။ သက်သေပြသည့် မက်ထရစ် — amplification factor နှင့် retry အချိုး။ ဥပမာ (ခ) အရ failure rate 0.50 နှင့် retry 3 ကြိမ်သည် amplification 1.875x ဖြစ်စေပြီး 10% retry budget က ထို တန်ဖိုးကို 1.100x တွင် ရပ်စေသည်။

**၄။ Circuit breaker နှင့် jitter policy သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Retry Budget၊ Graceful Degradation၊ Saturation။ သက်သေပြသည့် မက်ထရစ် — 10 ms bucket တစ်ခုအတွင်း peak request အရေအတွက်။ ဥပမာ (ခ) အရ jitter သည် peak ကို 20000.00 req/s မှ 2200.00 req/s သို့ လျှော့ချသည်၊ breaker သည် ပွင့်နေသည့် အချိန်အတွင်း retry ကို ဖြတ်တောက်သည်။

**၅။ Error budget နှင့် release policy သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Service Level Indicator (SLI)၊ Service Level Objective (SLO)၊ Error Budget၊ Canary Release၊ Rollback။ သက်သေပြသည့် မက်ထရစ် — burn rate နှင့် ကျန်ရှိသည့် budget အချိုး။ SLO 99.9% နှင့် requests/day 1,000,000 ဖြစ်သည့် စနစ်တွင် 30 ရက် window ၏ budget သည် request 30,000 ခု သို့မဟုတ် 100% ချို့ယွင်းမှု 43.20 မိနစ် နှင့် ညီမျှသည်၊ ထို့ကြောင့် burn rate 2.0x တွင် 15.00 ရက်အတွင်း ကုန်ဆုံးမည်ကို ကြိုတင် သိရမည်။

**၆။ Redundancy အတွက် ကုန်ကျစရိတ် သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Availability၊ Incident Response၊ Postmortem၊ Rollback။ သက်သေပြသည့် မက်ထရစ် — နှစ်စဉ် မျှော်မှန်း ကုန်ကျစရိတ် နှင့် break-even outage အကြိမ်ရေ။ ဥပမာ (ဂ) အရ hot standby သည် USD 28733/နှစ် ချွေတာပြီး break-even သည် တစ်နှစ်လျှင် outage 1.00 ကြိမ် ဖြစ်သည်။ ထို အကြိမ်ရေအောက်တွင် replica ထားခြင်းသည် ကုန်ကျစရိတ် ပိုများသည်။
