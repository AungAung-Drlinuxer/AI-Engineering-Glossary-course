# 03 — သီအိုရီမှ ထုတ်လုပ်မှု အခြေခံအဆောက်အအုံသို့ (Theory to Infrastructure)

ဤစာတမ်းသည် နယ်ပယ် ၀၈ ၏ term ၂၃ ခုလုံးကို အခြေခံအဆောက်အအုံ အမြင်ဖြင့် ပြန်လည် ဖတ်သည်။ AI-native development ၏ term တစ်ခုသည် workflow တစ်ခုအတွင်း သီအိုရီ အဖြစ်သာ မကျန်ရပါ။ ၎င်းသည် context ပမာဏ၊ token ကုန်ကျစရိတ်၊ review အချိန်၊ ပေါင်းစည်းပြီးသည့် ပြောင်းလဲမှု အရေအတွက်၊ merged change တစ်ခုလျှင် ကုန်ကျစရိတ် သို့မဟုတ် ထုတ်လုပ်မှု တုံ့ပြန်မှု အနက် တစ်ခုခုကို ရွေ့လျားစေသည်။ ရွေ့လျားသည့် ကိန်းဂဏန်း တစ်ခုစီသည် ထုတ်လုပ်မှု အခြေအနေတွင် တုံ့ပြန်ရမည့် ဆုံးဖြတ်ချက် တစ်ခုစီနှင့် တွဲလျက် ရှိသည်။

ဤစာတမ်းရှိ ကိန်းဂဏန်း အားလုံးသည် `guides/08_ai_native_development/scripts/` အောက်ရှိ Python script များမှ ရရှိသည့် တန်ဖိုးများ ဖြစ်သည်။ model စျေးနှုန်း၊ reviewer နှုန်း၊ defect နှုန်း နှင့် wall-clock ကုန်ကျစရိတ် အပေါ် မှီခိုသည့် တန်ဖိုးတိုင်းကို `ယူဆချက် (assumption)` အဖြစ် မှတ်သားထားသည်၊ အကြောင်းမှာ ထို တန်ဖိုးများသည် vendor၊ အဖွဲ့အစည်း နှင့် အချိန် အလိုက် ကွာခြားသည်။ ဤစာတမ်းသည် benchmark ရလဒ် များကို ဖော်ပြခြင်း မပြုပါ။ ဖော်ပြသည့် တန်ဖိုး အားလုံးသည် ဖော်မြူလာ နှင့် ယူဆချက် မှ တွက်ချက်ထားသည့် တန်ဖိုးများ ဖြစ်သည်။

## ၁။ ဝင်ရိုး ခြောက်ခု၏ ဝေါဟာရ သတ်မှတ်ချက်

နောက်ပိုင်း အပိုင်းများတွင် ဤဝေါဟာရ ခြောက်ခုကို တူညီသည့် အဓိပ္ပာယ်ဖြင့်သာ အသုံးပြုမည် ဖြစ်သည်။

**context and memory footprint** — agent တစ်ခု လုပ်ငန်း တစ်ခုကို လုပ်ဆောင်ရာတွင် context အဖြစ် တင်သည့် token ပမာဏ နှင့် ဖိုင်၊ map၊ state များ အတွက် ကိုင်ဆောင်ထားသည့် memory ဖြစ်သည်။ ၎င်းသည် context window ထဲ ဆံ့မှုကို အမာခံ ကန့်သတ်သည်၊ ထို့ကြောင့် ဤဝင်ရိုးသည် မကျော်လွန်နိုင်သည့် နယ်နိမိတ် ဖြစ်သည်။

**compute and token cost** — လုပ်ငန်းတစ်ခုအတွက် ကုန်သည့် input/output token ပမာဏ နှင့် provider ကောက်ခံငွေ ဖြစ်သည်။ retry၊ ကျရှုံးသည့် run နှင့် tool ခေါ်ဆိုမှု များ ထပ်ပေါင်းလျှင် ဤကိန်း ကြီးထွားသည်။

**wall-clock and review time** — လူ နှင့် agent စောင့်ရသည့် အချိန် ဖြစ်သည်။ review လုပ်ရမည့် စာကြောင်း အရေအတွက် နှင့် reviewer ၏ capacity က ၎င်းကို ဆုံးဖြတ်သည်။

**throughput of merged changes** — အချိန် တစ်ခုအတွင်း test အောင်ပြီး review လုပ်ပြီး ပေါင်းစည်းနိုင်သည့် ပြောင်းလဲမှု အရေအတွက် ဖြစ်သည်။ ၎င်းကို agent run အရေအတွက်ဖြင့် မတိုင်းရ၊ လက်ခံရရှိသည့် patch ဖြင့်သာ တိုင်းရသည်။

**cost per change** — merged change တစ်ခုလျှင် ကုန်ကျသည့် စုစုပေါင်း စရိတ် ဖြစ်သည်။ retry၊ ကျရှုံးသည့် run၊ tool အသုံးပြုမှု၊ evaluation နှင့် လူ၏ ပြုပြင်မှု အားလုံး ပါဝင်သည်။

**production consequence** — ထို concept ကို လျစ်လျူရှုလျှင် ထုတ်လုပ်မှု တွင် မည်သည့် အရာ ကျိုးပျက်မည်ကို ဆိုလိုသည်။ ဥပမာ reviewer agent ကို rubric မပါဘဲ ခေါ်ဆိုလျှင် ကုန်ကျစရိတ် တိုးသော်လည်း ဖမ်းမိသည့် အမှား မတိုးခြင်းသည် ထုတ်လုပ်မှု အကျိုးဆက် ဖြစ်သည်။

## ၃။ term အလိုက် ရှင်းလင်းချက်

term များကို မိသားစု ခြောက်ခုဖြင့် စုစည်းထားသည် — (က) context and memory footprint၊ (ခ) compute and token cost၊ (ဂ) wall-clock and review time၊ (ဃ) throughput of merged changes၊ (င) cost per change၊ (စ) production consequence ဖြစ်သည်။ ဤအုပ်စုခွဲမှုသည် အပိုင်း ၂ ၏ ဇယားနှင့် တိုက်ရိုက် ကိုက်ညီသည်။

### မိသားစု (က) — context and memory footprint

#### Progressive Disclosure

Progressive Disclosure သည် လူ တစ်ဦး သို့မဟုတ် မော်ဒယ် တစ်ခုအား အနည်းဆုံး အသုံးဝင်သည့် context ကို အရင်ပေးပြီး၊ လုပ်ငန်း သို့မဟုတ် အထောက်အထား လိုအပ်လာသည့်အခါမှ ပိုမို နက်ရှိုင်းသည့် အသေးစိတ်ကို ဖော်ထုတ်ပေးခြင်း ဖြစ်သည်။ အခြေခံအဆောက်အအုံ အရ ၎င်းသည် context token ပမာဏကို ကန့်သတ်သည့် knob ဖြစ်သည်၊ ဥပမာ (က) တွင် whole-repo context သည် round တစ်ခုလျှင် 378,000 token လိုအပ်သော်လည်း retrieval-scoped context သည် 5,040 token ဖြင့် လုံလောက်သည်။ ထိုကွာခြားမှုသည် လုပ်ငန်းတစ်ခုလျှင် USD 6.8670 မှ USD 0.1537 သို့ ကျဆင်းခြင်း ဖြစ်သည်။ သို့သော် ဆုံးဖြတ်ချက်အတွက် လိုအပ်သည့် အထောက်အထားကို တမင်တကာ မပေးခြင်းသည် Progressive Disclosure မဟုတ်ပါ၊ ၎င်းသည် အဆင့်လိုက် ဝင်ရောက်ခြင်းသာ ဖြစ်သည်။

#### Repository Instructions

Repository Instructions သည် coding agent များအား repository တစ်ခု မည်သို့ ဖွဲ့စည်းထားသည်၊ မည်သည့် command နှင့် စည်းမျဉ်းများ သက်ဆိုင်သည်၊ မည်သည့် နယ်နိမိတ်များကို လေးစားရမည် နှင့် အလုပ်ကို မည်သို့ စစ်ဆေးရမည် ကို ပြောပြသည့် version control ဖြင့် စီမံထားသည့် လမ်းညွှန်ချက် ဖြစ်သည်။ အခြေခံအဆောက်အအုံ အရ ၎င်းသည် ထပ်ခါတလဲလဲ နှုတ်ဖြင့် ပြောဆိုရသည့် အဖွဲ့အစည်း အတွင်းသိ အသိပညာကို ကုဒ်နှင့်အတူ လိုက်ပါပြီး ပရောဂျက် အခွဲအလိုက် ကွာခြားနိုင်သည့် context အဖြစ် ပြောင်းလဲပေးသည်။ ၎င်း၏ ကုန်ကျစရိတ်သည် ဖိုင် အရေအတွက် အလိုက် တိုးသည့် context token ဖြစ်သည်၊ ထို့ကြောင့် ဖိုင် များလွန်းလျှင် အကျိုးအမြတ် ပြောင်းပြန် ဖြစ်နိုင်သည်။ Repository Instructions သည် source code နှင့် လူဖတ်သည့် documentation ကို ဖြည့်စွက်ပေးသည်၊ အသုံးပြုသူ၏ လက်ရှိ တောင်းဆိုမှုကို ကျော်လွှားခြင်း သို့မဟုတ် agent များ လိုက်နာမည်ဟု အာမခံခြင်း မပြုပါ။

#### Repository Map

Repository Map သည် repository တစ်ခု၏ အရေးပါသည့် directory များ၊ ပိုင်ဆိုင်မှု နယ်နိမိတ်များ၊ entry point များ၊ build command များ၊ test များ၊ generated ဖိုင်များ နှင့် local လမ်းညွှန်ချက်များကို ကျစ်လျစ်စွာ ထိန်းသိမ်းထားသည့် ဖော်ပြချက် ဖြစ်သည်။ ၎င်းသည် coding agent အား ကြီးမားသည့် ဖိုင်များ မဖွင့်မီ မှန်ကန်သည့် အထောက်အထားကို ရှာတွေ့နိုင်ရန် ကူညီသည်၊ ဆိုလိုသည်မှာ ဖတ်ရမည့် token ပမာဏကို ကြိုတင် ကန့်သတ်ခြင်း ဖြစ်သည်။ အကြမ်းဖျင်း ဖိုင် tree သည် အမည်များကို ပြသည်၊ repository map သည် မည်သည့် path များ အရေးပါသည် နှင့် လုပ်ငန်းတစ်ခုနှင့် မည်သို့ ဆက်စပ်သည်ကို ရှင်းပြသည်။ ထို့ကြောင့် ၎င်းသည် progressive disclosure ၏ ပထမဆုံး အလွှာ အဖြစ် အသုံးပြုရမည့် artifact ဖြစ်သည်။

### မိသားစု (ခ) — compute and token cost

#### Coding Agent

Coding Agent သည် repository ကို စစ်ဆေးနိုင်ခြင်း၊ ဖိုင်များ တည်းဖြတ်နိုင်ခြင်း၊ development tool များ လုပ်ဆောင်နိုင်ခြင်း စသည့် လုပ်ဆောင်ချက်များဖြင့် သတ်မှတ်ထားသည့် အင်ဂျင်နီယာ လုပ်ငန်းတစ်ခုကို တိုးတက်စေနိုင်သည့် agent ဖြစ်သည်။ token ကုန်ကျစရိတ် အမြင်ဖြင့် ၎င်းသည် round တစ်ခုစီတွင် context အားလုံးကို ပြန်ပို့သည့် စနစ် ဖြစ်သည်၊ ဥပမာ (က) တွင် ၆ round ဖြင့် whole-repo context ကို အသုံးပြုလျှင် input token သည် 2,268,000 အထိ ရောက်သည်။ ၎င်း၏ တန်ဖိုးသည် ကုဒ် ထုတ်လုပ်နိုင်သည့် အရည်အသွေးအပေါ်တွင်သာ မဟုတ်ဘဲ repository context၊ tool ခွင့်ပြုချက်များ၊ review နယ်နိမိတ်များ နှင့် verification အပေါ်တွင်လည်း မူတည်သည်။ စာသား အကြံပြုချက်သာ ပေးသည့် coding assistant သည် agent ဖြစ်ရန် မလိုအပ်ပါ၊ agent သည် tool များမှတစ်ဆင့် လုပ်ဆောင်ပြီး ရလဒ်များကို စောင့်ကြည့်သည်။

#### Model Router

Model Router သည် capability၊ latency၊ ကုန်ကျစရိတ်၊ context အရွယ်အစား၊ policy နှင့် လက်ရှိ ရရှိနိုင်မှု စသည့် လိုအပ်ချက်များကို အသုံးပြု၍ request တစ်ခုအတွက် မော်ဒယ် သို့မဟုတ် provider ကို ရွေးချယ်သည့် component ဖြစ်သည်။ ၎င်း၏ အကျိုးအမြတ်သည် request တိုင်းကို အကြီးမားဆုံး ရွေးချယ်မှုသို့ မပို့ဘဲ လုပ်ငန်းအလိုက် သင့်တော်သည့် မော်ဒယ်သို့ ပို့ခြင်းဖြင့် ရရှိသည်၊ ဆိုလိုသည်မှာ routed ရာခိုင်နှုန်းသည် cost per token ကို တိုက်ရိုက် ရွေ့လျားစေသည်။ routing သည် policy ဆုံးဖြတ်ချက် ဖြစ်သည်၊ ကျပန်း load balancing သည် traffic ကို ခွဲဝေပေးရုံသာ ဖြစ်သည်။ လက်တွေ့တွင် အန္တရာယ် နည်းသည့် extraction ကို မြန်သည့် မော်ဒယ်သို့ ပို့ပြီး၊ တူညီသည့် data policy ကို ဖြည့်ဆည်းသည့် provider များသို့သာ fail over လုပ်ရမည်။

#### Rate Limit

Rate Limit သည် သတ်မှတ်ထားသည့် အချိန် သို့မဟုတ် capacity အပိုင်းအခြားအတွင်း request များ၊ token များ၊ တစ်ပြိုင်နက် လုပ်ဆောင်သည့် အလုပ်များ သို့မဟုတ် အခြား အရင်းအမြစ် တစ်ခုကို အများဆုံး ခွင့်ပြုသည့် policy ဖြစ်သည်။ အခြေခံအဆောက်အအုံ အရ ၎င်းသည် ကုန်ကျစရိတ်၏ အပေါ်ကန့်သတ်ချက် (ceiling) ကို သတ်မှတ်သည်၊ အကြောင်းမှာ ခွင့်ပြုထားသည့် token အရေအတွက်ကို ကျော်လွန်၍ သုံးစွဲနိုင်ခြင်း မရှိပါ။ ၎င်းသည် provider များ နှင့် မိမိ စနစ်ကို ဝန်ပိမှု၊ မထိန်းချုပ်နိုင်သည့် အသုံးစရိတ် နှင့် တရားမျှတမှု မရှိသည့် အရင်းအမြစ် အသုံးပြုမှုမှ ကာကွယ်သည်။ Rate Limit သည် ခွင့်ပြုထားသည့် အသုံးပြုမှုကို ထိန်းချုပ်သည်၊ Backpressure သည် အောက်ပိုင်း capacity ကန့်သတ်ချက်များကို စနစ်တစ်လျှောက် ဖြန့်ဝေပေးသည်။

#### Retry with Backoff

Retry with Backoff သည် ယာယီ ပျက်ကွက်သည့် လုပ်ဆောင်ချက်ကို တစ်ဆင့်ချင်း ပိုရှည်သည့် ကြားချိန်များဖြင့် ထပ်လုပ်ခြင်း ဖြစ်ပြီး၊ များသောအားဖြင့် ကျပန်း jitter နှင့် တင်းကျပ်သည့် retry အရေအတွက် ကန့်သတ်ချက် ပါဝင်သည်။ ကုန်ကျစရိတ် အမြင်ဖြင့် retry တိုင်းသည် token၊ wall-clock နှင့် capacity ကို ထပ်မံ စားသုံးသည်၊ ဥပမာ (ဂ) တွင် success rate 0.62 အောက်တွင် လုပ်ငန်း ၁၀၀ ခုအတွက် ပိုလျှံသည့် attempt 57.93 ခု ဖြစ်ပေါ်သည်။ ချက်ချင်း တစ်ပြိုင်နက် ပြန်လုပ်သည့် retry များသည် ပျက်ယွင်းမှုကို ပို၍ ဆိုးစေနိုင်သည်၊ rate limit များကို ကုန်ဆုံးစေနိုင်သည် နှင့် ဘေးထွက် အကျိုးသက်ရောက်မှုများကို ထပ်နှစ်ဆ ဖြစ်စေနိုင်သည်။ အမြဲတမ်း ဖြစ်သည့် validation သို့မဟုတ် ခွင့်ပြုချက် error များကို ပြန်မလုပ်ရ၊ ထပ်နှစ်ဆ ဖြစ်မှု ကာကွယ်သည့် နည်းလမ်း မရှိဘဲ idempotency မရှိသည့် လုပ်ဆောင်ချက်များကို ပြန်မလုပ်ရ။

#### Semantic Cache

Semantic Cache သည် ရွေးချယ်ထားသည့် ကိုယ်စားပြုပုံစံ နှင့် ကန့်သတ်တန်ဖိုးတစ်ခုအောက်တွင် request အသစ်တစ်ခုကို လုံလောက်စွာ ဆင်တူသည်ဟု သတ်မှတ်သည့်အခါ ယခင် ရလဒ်ကို ပြန်လည် အသုံးပြုသည့် cache ဖြစ်သည်။ ၎င်းသည် ထပ်ခါတလဲလဲ ရည်ရွယ်ချက်များအတွက် latency နှင့် ကုန်ကျစရိတ်ကို လျှော့ချနိုင်သည်၊ cache hit rate သည် ထို အကျိုးအမြတ်၏ တိုက်ရိုက် ကိန်း ဖြစ်သည်။ သို့သော် မှားယွင်းသည့် ကိုက်မည့်မှုတစ်ခုသည် ခေတ်မမီတော့သည့် သို့မဟုတ် အသုံးပြုသူအတွက် မသင့်လျော်သည့် output ကို ပြန်ပေးနိုင်သည်၊ ထို့ကြောင့် ဤချွေတာမှုသည် quality အန္တရာယ် နှင့် လဲလှယ်ရသည်။ Semantic similarity သည် request နှစ်ခုတွင် တူညီသည့် မှန်ကန်သည့် အဖြေ ရှိသည်ဟု အာမခံခြင်း မပြုပါ။

### မိသားစု (ဂ) — wall-clock and review time

#### Flaky Test

Flaky Test သည် ကုဒ် သို့မဟုတ် ရည်ရွယ်ထားသည့် test ပတ်ဝန်းကျင်တွင် သက်ဆိုင်သည့် ပြောင်းလဲမှု မရှိဘဲ တူညီသည့် run များတွင် အောင်နိုင်ခြင်း နှင့် ကျရှုံးခြင်း နှစ်မျိုးလုံး ဖြစ်နိုင်သည့် test ဖြစ်သည်။ အချိန် အမြင်ဖြင့် ၎င်းသည် reviewer ၏ ကန့်သတ်ထားသည့် capacity ကို မှားယွင်းသည့် အထောက်အထား အပေါ် ဖြုန်းတီးစေသည်၊ ဥပမာ (ခ) တွင် capacity 480 မိနစ်သာ ရှိသည့်အတွက် ထပ်လုပ်ရသည့် run တိုင်းသည် တကယ့် review အလုပ်မှ မိနစ်များကို နုတ်ယူသည်။ Flakiness သည် verification gate များကို အားနည်းစေပြီး၊ တကယ့် ပျက်ကွက်မှုများကို လူများ သို့မဟုတ် agent များ လျစ်လျူရှုစေရန် သို့မဟုတ် မှားယွင်းသည့် အောင်မြင်မှု ရသည်အထိ ထပ်ခါတလဲလဲ လုပ်စေရန် လေ့ကျင့်ပေးနိုင်သည်။ ရံဖန်ရံခါ ပေါ်သည့် product bug ကို အမြဲတမ်း ဖော်ထုတ်ပြသည့် test သည် အဖိုးတန်သည့် အထောက်အထား ဖြစ်ပြီး၊ flaky test ဖြစ်ရန် မလိုအပ်ပါ။

#### Handoff

Handoff သည် လူများ သို့မဟုတ် agent များအကြား လုပ်ငန်းတစ်ခုကို ဖွဲ့စည်းပုံကျကျ လွှဲပြောင်းခြင်း ဖြစ်ပြီး၊ ပန်းတိုင်၊ လက်ရှိ အခြေအနေ၊ အထောက်အထား၊ ဆုံးဖြတ်ချက်များ၊ ကန့်သတ်ချက်များ နှင့် ကျန်ရှိသည့် အလုပ်များကို ထိန်းသိမ်းပေးသည်။ အခြေခံအဆောက်အအုံ အရ ၎င်းသည် context ကို ပြန်လည် ဖန်တီးခြင်း၏ ကုန်ကျစရိတ်ကို လျှော့ချသည်၊ အကြောင်းမှာ လုပ်သူအသစ်သည် ရှည်လျားသည့် transcript တစ်ခုလုံးကို ဖတ်ရန် မလိုတော့ဘဲ ကျစ်လျစ်သည့် task packet ကို ဖတ်ရုံသာ ဖြစ်သည်။ ကောင်းမွန်သည့် handoff သည် နောက်လုပ်သူအား လုပ်ငန်းတစ်ခုလုံးကို ပြန်လည် တည်ဆောက်ရခြင်း သို့မဟုတ် ပြီးစီးပြီးသား လုပ်ဆောင်မှုများကို ထပ်လုပ်ရခြင်းမှ ကာကွယ်ပေးသည်။ Summary သည် မည်သည့် အရာ ဖြစ်ပွားခဲ့သည်ကို ဆိုသည်၊ Handoff သည် မည်သည့် အခြေအနေက အခွင့်အာဏာ ရှိသည်နှင့် နောက်တွင် မည်သည့် အရာ လုပ်ရမည်ကို ထပ်မံ ဆိုသည်။

#### Patch

Patch သည် သိထားသည့် base revision တစ်ခုနှင့် နှိုင်းယှဉ်၍ ထည့်သည့် စာကြောင်းများ နှင့် ဖြတ်သည့် စာကြောင်းများအဖြစ် ဖော်ပြလေ့ရှိသည့်၊ ဖိုင်တစ်ခု သို့မဟုတ် တစ်ခုထက်ပိုသည့် ဖိုင်များသို့ ပြောင်းလဲမှုများကို review လုပ်နိုင်သည့် ပုံစံဖြင့် ဖော်ပြချက် ဖြစ်သည်။ review အချိန် အမြင်ဖြင့် ၎င်း၏ တန်ဖိုးသည် မျက်နှာပြင် ကျဉ်းမှု အပေါ် မူတည်သည်၊ ဥပမာ (ခ) တွင် 1,200 စာကြောင်းအတွက် 300 review မိနစ် လိုအပ်သည်ဟု တွက်ချက်သည်။ Patch သည် လူများ နှင့် agent များအား working directory တစ်ခုလုံးကို လက်ခံရမည့်အစား ကျဉ်းမြောင်းသည့် artifact တစ်ခုကို စစ်ဆေးခြင်း၊ test လုပ်ခြင်း၊ အသုံးချခြင်း သို့မဟုတ် ပယ်ချခြင်း ပြုလုပ်နိုင်စေသည်။ Patch သည် ဖိုင် ပြောင်းလဲမှုများကို ဖမ်းယူသည်၊ ၎င်းတို့ကို ဖြန့်ချိရန် လိုအပ်သည့် ကျိုးကြောင်းဆင်ခြင်မှု၊ test အထောက်အထား သို့မဟုတ် ခွင့်ပြုချက်ကို ဖမ်းယူခြင်း မဟုတ်ပါ။

#### Reviewer Agent

Reviewer Agent သည် အခြား agent တစ်ခု၏ artifact သို့မဟုတ် ဆုံးဖြတ်ချက်ကို တိကျသည့် စံချိန်စံညွှန်းများအပေါ် စစ်ဆေးပြီး၊ တွေ့ရှိချက်များ သို့မဟုတ် အဆုံးအဖြတ်တစ်ခုကို ပြန်ပေးရန် တာဝန်ပေးထားသည့် agent ဖြစ်သည်။ ၎င်းသည် အချိန် နှင့် token နှစ်ခုလုံးကို ထပ်တိုးစေသည့် လုပ်ငန်း ဖြစ်သည်၊ ထို့ကြောင့် ဤအပိုကုန်ကျစရိတ်ကို ဖမ်းမိသည့် finding အရေအတွက်နှင့် နှိုင်းယှဉ်ရမည်။ အခန်းကဏ္ဍ ခွဲခြားထားခြင်းသည် ချန်လှပ်ထားမှုများကို ဖမ်းမိနိုင်သည်၊ သို့သော် reviewer သည် သီးခြားလွတ်လပ်သည့် အထောက်အထား နှင့် တိကျသည့် rubric ရရှိမှသာ အကျိုးရှိသည်။ ဒုတိယ မော်ဒယ် ခေါ်ဆိုမှုတစ်ခုသည် အလိုအလျောက် လွတ်လပ်သည် သို့မဟုတ် မှန်ကန်သည် မဟုတ်ပါ၊ မျှဝေထားသည့် context၊ မော်ဒယ်၏ bias နှင့် မပီပြင်သည့် စံချိန်စံညွှန်းများသည် တူညီသည့် အမှားကို ပြန်ဖြစ်စေနိုင်သည်။

#### Worktree

Worktree သည် Git တွင် repository တစ်ခု နှင့် branch သို့မဟုတ် commit တစ်ခုနှင့် ချိတ်ဆက်ထားသည့် working directory တစ်ခု ဖြစ်ပြီး၊ object storage ကို မျှဝေသုံးစွဲသော်လည်း ကိုယ်ပိုင် checked-out ဖိုင်များ နှင့် index ရှိသည်။ အချိန် အမြင်ဖြင့် ၎င်းသည် checkout တစ်ခုတည်းကို ခဏခဏ လဲလှယ်ခြင်း သို့မဟုတ် ထပ်ရေးခြင်းမှ ဖြစ်ပေါ်သည့် စောင့်ချိန်ကို ဖယ်ရှားသည်၊ ဆိုလိုသည်မှာ လူ နှင့် agent များ တစ်ပြိုင်နက် အလုပ်လုပ်နိုင်သည်။ Worktree သည် checked-out ဖိုင်များကို သီးခြားခွဲခြားပေးသည်၊ စက်ပေါ်ရှိ process၊ port၊ cache၊ database သို့မဟုတ် secret တိုင်းကို သီးခြားခွဲခြားပေးခြင်း မဟုတ်ပါ။ လက်တွေ့တွင် coding agent တစ်ခုချင်းစီအား အမည်ပေးထားသည့် feature branch နှင့် တိကျသည့် worktree path ပေးပြီး၊ ပုံမှန် Git history အတိုင်း patch များကို review လုပ်ပြီး ပေါင်းစည်းရမည်။

### မိသားစု (ဃ) — throughput of merged changes

#### Backpressure

Backpressure သည် အောက်ပိုင်း component တစ်ခုသည် လက်ရှိ နှုန်းအတိုင်း လုပ်ငန်းကို လုံခြုံစွာ မလုပ်ဆောင်နိုင်သည့်အခါ အပေါ်ပိုင်း (upstream) အလုပ်ကို နှေးကွေးစေခြင်း သို့မဟုတ် လက်မခံဘဲ ပယ်ချခြင်းဖြင့် flow ကို ထိန်းချုပ်သည့် ယန္တရား ဖြစ်သည်။ throughput အမြင်ဖြင့် ၎င်းသည် queue depth ကို ကန့်သတ်ထားခြင်းဖြင့် လက်ခံရရှိသည့် အလုပ်အရေအတွက် အစား ပြီးစီးသည့် အလုပ်အရေအတွက်ကို ထိန်းသည်။ Backpressure မရှိပါက တန်းစီနေသည့် agent run များ၊ tool call များ သို့မဟုတ် stream ဖြင့် ပို့သည့် event များသည် memory ကို ကုန်ဆုံးစေနိုင်သည်၊ rate limit ကို ကျော်လွန်စေနိုင်သည်၊ retry များကို ပို၍ ဆိုးရွားစွာ မြှင့်တင်နိုင်သည်။ Backpressure သည် ပျက်ကွက်မှု မဖြစ်မီတွင် capacity ကို ကာကွယ်သည်၊ Circuit Breaker သည် dependency တစ်ခု ကျန်းမာမှု မရှိတော့ကြောင်း ပျက်ကွက်မှုများ ပေါ်ထွက်ပြီးမှ ခေါ်ဆိုမှုများကို ရပ်တန့်သည်။

#### Scope Contract

Scope Contract သည် လုပ်ငန်းတစ်ခု၏ ပန်းတိုင်၊ ခွင့်ပြုထားသည့် နှင့် တားမြစ်ထားသည့် မျက်နှာပြင်များ၊ မျှော်လင့်သည့် artifact များ၊ verification လိုအပ်ချက်များ နှင့် ရပ်တန့်မည့် အခြေအနေများကို သတ်မှတ်သည့် တိကျသည့် သဘောတူညီချက် ဖြစ်သည်။ ၎င်းသည် review လုပ်ရမည့် မျက်နှာပြင် ပမာဏကို ကြိုတင် ကန့်သတ်သည့်အတွက်၊ လက်ခံရရှိသည့် ပြောင်းလဲမှု အရေအတွက် (throughput) ကို ထိန်းသည်။ ၎င်းသည် agent အား ကျဉ်းမြောင်းသည့် ပြင်ဆင်မှုကို review မလုပ်နိုင်သည့် ပြန်လည် ဖွဲ့စည်းမှုအဖြစ် ပြောင်းလဲခြင်း သို့မဟုတ် အထောက်အထား မရှိဘဲ ပြီးစီးပြီဟု ဆိုခြင်းမှ ကာကွယ်သည်။ လုပ်ငန်း ဖော်ပြချက်သည် မည်သည့် အရာကို လိုချင်သည်ကို ဆိုသည်၊ Scope contract သည် နယ်နိမိတ်များ နှင့် သက်သေကို ထပ်မံ သတ်မှတ်သည်။

#### Test Oracle

Test Oracle သည် စောင့်ကြည့်ရသည့် program အပြုအမူ မှန်ကန်ခြင်း ရှိ၊ မရှိ ဆုံးဖြတ်ရန် အသုံးပြုသည့် ယန္တရား၊ သတ်မှတ်ချက်၊ ရည်ညွှန်းမှု၊ invariant သို့မဟုတ် လူ၏ ဆုံးဖြတ်ချက် ဖြစ်သည်။ အခြေခံအဆောက်အအုံ အရ ၎င်းသည် verification ကို အလိုအလျောက် လုပ်နိုင်သည့် အပိုင်းအခြားကို ဆုံးဖြတ်သည်၊ ဆိုလိုသည်မှာ လူ ပါဝင်ရမည့် ရာခိုင်နှုန်းက ပေါင်းစည်းနိုင်သည့် နှုန်းကို ကန့်သတ်သည်။ test input များ ထုတ်လုပ်နိုင်ခြင်းဖြင့် မလုံလောက်ပါ၊ အလိုအလျောက် verification အတွက် ရလဒ်တစ်ခုချင်းစီကို အမျိုးအစားခွဲရန် လွတ်လပ်သည့် အခြေခံတစ်ခု လိုအပ်သည်။ ကုဒ်ကို ရေးသည့် မော်ဒယ်ကို ၎င်း၏ ကိုယ်ပိုင် output မှန်ကန်သည်၊ မမှန်ကန် မေးခြင်းဖြင့် လွတ်လပ်သည့် oracle အဖြစ် သဘောထားရမည် မဟုတ်ပါ။

### မိသားစု (င) — cost per change

#### Cost per Successful Task

Cost per Successful Task သည် သတ်မှတ်ထားသည့် အောင်မြင်မှု စံချိန်စံညွှန်းကို ဖြည့်ဆည်းသည့် လုပ်ငန်း အရေအတွက်ဖြင့် စုစုပေါင်း စနစ် ကုန်ကျစရိတ်ကို စားခြင်း ဖြစ်သည်၊ ထိုတွင် retry များ၊ ကျရှုံးသည့် run များ၊ tool အသုံးပြုမှု နှင့် evaluation အတွက် အပိုကုန်ကျစရိတ်များ ပါဝင်သည်။ ဥပမာ (ဂ) က ဤခြားနားချက်ကို ကိန်းဖြင့် ပြသည် — attempt တစ်ခု၏ ကုန်ကျစရိတ်သည် USD 4.5270 ဖြစ်သော်လည်း merged change တစ်ခုလျှင် ကုန်ကျစရိတ်သည် USD 7.3016 ဖြစ်သည်၊ အကြောင်းမှာ ကျရှုံးသည့် attempt များလည်း ကျခံရသည်။ ထို့ကြောင့် စျေးသက်သာသည့် မော်ဒယ် ခေါ်ဆိုမှုတစ်ခုသည် မကြာခဏ ကျရှုံးခြင်း သို့မဟုတ် လူဖြင့် ထပ်ခါတလဲလဲ ပြုပြင်ရခြင်း ဖြစ်ပါက ကုန်ကျစရိတ် ကြီးမားသည့် workflow တစ်ခု ဖြစ်လာနိုင်သည်။ Cost per token သည် အသုံးပြုမှုကို တိုင်းတာသည်၊ Cost per successful task သည် အသုံးဝင်သည့် ရလဒ်များကို တိုင်းတာသည်။

#### Trace

Trace သည် မော်ဒယ် ခေါ်ဆိုမှုများ၊ retrieval၊ tool များ၊ အခြေအနေ ပြောင်းလဲမှုများ၊ retry များ၊ ခွင့်ပြုချက်များ နှင့် evaluation များ တစ်လျှောက် request တစ်ခု သို့မဟုတ် လုပ်ငန်းတစ်ခု၏ ဆက်စပ်နေသည့် မှတ်တမ်း ဖြစ်သည်။ cost per change ကို တွက်ရန် ၎င်းသည် မရှိမဖြစ် ဖြစ်သည်၊ အကြောင်းမှာ အချိန်၊ ကုန်ကျစရိတ် နှင့် ပျက်ကွက်မှု မည်သည့် အဆင့်မှ ဝင်ရောက်လာသည်ကို ပြန်လည် တည်ဆောက်နိုင်စေသည်။ ဤအချက်သည် ကြီးမားသည့် စနစ်တွင် ကုန်ကျစရိတ် တာဝန်ကို အဆင့်အလိုက် ခွဲခြားရန် အခြေခံ ဖြစ်သည်။ Trace သည် လုပ်ငန်း ဆိုင်ရာ အထောက်အထားကို မှတ်တမ်းတင်ရမည်၊ ဖုံးကွယ်ထားသည့် မော်ဒယ် ကျိုးကြောင်းဆင်ခြင်မှု၊ secret များ သို့မဟုတ် redact မလုပ်ရသေးသည့် အရေးပါသည့် အကြောင်းအရာများကို ဖော်ထုတ်ခြင်း မဟုတ်ပါ။

### မိသားစု (စ) — production consequence

#### Circuit Breaker

Circuit Breaker သည် ပျက်ကွက်မှုများ သတ်မှတ်ထားသည့် အဆင့်တစ်ခုကို ကျော်လွန်သည့်အခါ dependency တစ်ခုသို့ ခေါ်ဆိုမှုများကို ခေတ္တရပ်ဆိုင်းပြီး၊ ထို့နောက် dependency ပြန်လည် ကောင်းမွန်လာခြင်း ရှိ၊ မရှိ စမ်းသပ် စစ်ဆေးသည့် ယုံကြည်စိတ်ချရမှု ထိန်းချုပ်ကိရိယာ ဖြစ်သည်။ ထုတ်လုပ်မှု အကျိုးဆက် အရ ၎င်းသည် မော်ဒယ် သို့မဟုတ် tool ၏ ထပ်ခါတလဲလဲ ပျက်ကွက်မှုများသည် ကျန်စနစ် တစ်ခုလုံးတွင် latency၊ budget နှင့် capacity ကို မစားသုံးစေရန် ကာကွယ်ပေးသည်။ Circuit breaker သည် dependency ၏ ကျန်းမာမှုကို တုံ့ပြန်သည်၊ Rate limit သည် ခွင့်ပြုထားသည့် request ပမာဏ ကို ထိန်းချုပ်သည်။ လက်တွေ့တွင် provider timeout များ ထပ်ခါတလဲလဲ ဖြစ်ပြီးနောက် breaker ကို ဖွင့်ခြင်း၊ fail over လုပ်ခြင်း သို့မဟုတ် ထိန်းချုပ်ထားသည့် တုံ့ပြန်ချက် ပြန်ပေးခြင်း ပြုလုပ်ပြီး၊ cooldown ကာလ ပြီးနောက် အကန့်အသတ်ရှိသည့် ကျန်းမာရေး စမ်းသပ်မှုကို ခွင့်ပြုရမည်။

#### Idempotency

Idempotency သည် တူညီသည့် identity ဖြင့် တူညီသည့် လုပ်ဆောင်ချက်ကို ထပ်ခါတလဲလဲ လုပ်သည့်အခါ ပထမဆုံး အောင်မြင်စွာ လုပ်ဆောင်ပြီးသည့် အကျိုးသက်ရောက်မှုထက် ပို၍ ဘေးထွက် အကျိုးသက်ရောက်မှု မဖြစ်ပေါ်စေသည့် ဂုဏ်သတ္တိ ဖြစ်သည်။ ထုတ်လုပ်မှု အကျိုးဆက် အရ ၎င်းသည် retry နှင့် မဖြစ်မနေ ဆက်စပ်သည်၊ ဖြန့်ကျက်ထားသည့် agent စနစ်များတွင် retry လုပ်ခြင်းသည် သာမန် ဖြစ်ပြီး၊ Idempotency မရှိပါက မသေချာသည့် တုံ့ပြန်ချက် တစ်ခုသည် ငွေပေးချေမှု၊ comment၊ deployment သို့မဟုတ် record များကို ထပ်နှစ်ဆ ဖြစ်စေနိုင်သည်။ Idempotency သည် တုံ့ပြန်ချက်တိုင်း byte တစ်လုံးမျှ မတူကွာခြားမှု မရှိရမည်ဟု မဆိုလိုပါ၊ ရည်ရွယ်ထားသည့် အခြေအနေ ပြောင်းလဲမှု ထပ်နှစ်ဆ မဖြစ်ခြင်းကို ဆိုလိုသည်။ လက်တွေ့တွင် tool request တစ်ခုတွင် idempotency key တစ်ခု တွဲထည့်ပြီး၊ ပြီးစီးသည့် ရလဒ်ကို မှတ်တမ်းတင်ထားရမည်။

#### Observability

Observability သည် မှတ်တမ်းတင်ထားသည့် input၊ output၊ အခြေအနေ ပြောင်းလဲမှုများ၊ tool ခေါ်ဆိုမှုများ၊ အချိန်တိုင်းတာမှုများ၊ ကုန်ကျစရိတ်များ၊ error များ နှင့် evaluation အချက်ပြမှုများမှ AI စနစ်တစ်ခု၏ အပြုအမူကို နားလည်နိုင်သည့် စွမ်းရည် ဖြစ်သည်။ ထုတ်လုပ်မှု အကျိုးဆက် အရ ၎င်းသည် ချို့ယွင်းသည့် နယ်နိမိတ်ကို ရှာဖွေချိန်ကို လျှော့ချပေးသည်၊ အကြောင်းမှာ AI ပျက်ကွက်မှုများသည် မော်ဒယ်၊ retrieval၊ tool များ နှင့် orchestration ကို ဖြတ်ကျော် ဖြစ်ပွားတတ်ပြီး၊ ဆက်စပ်နေသည့် အထောက်အထား လိုအပ်သည်။ Logging သည် event များကို စုဆောင်းသည်၊ Observability သည် ထို event များကို ဖွဲ့စည်းပုံကျပြီး အပြန်အလှန် ဆက်စပ်မှု ရှိစေကာ လုပ်ငန်း မေးခွန်းများကို ဖြေနိုင်အောင် ပြုလုပ်သည်။ လက်တွေ့တွင် retrieval၊ မော်ဒယ် ခေါ်ဆိုမှု၊ tool လုပ်ဆောင်မှု၊ ခွင့်ပြုချက်များ နှင့် နောက်ဆုံး အမှတ်ပေးခြင်း တစ်လျှောက် trace ID တစ်ခုကို မှတ်တမ်းတင်ပြီး၊ redaction နှင့် ဝင်ရောက်မှု ထိန်းချုပ်ချက်များကို ကျင့်သုံးရမည်။

#### Regression Test

Regression Test သည် အလုပ်လုပ်ကြောင်း သိထားသည့် အပြုအမူကို ကာကွယ်ပေးသည့် ထပ်ခါတလဲလဲ လုပ်နိုင်သည့် စစ်ဆေးမှု ဖြစ်သည်၊ အထူးသဖြင့် ကုဒ်၊ prompt၊ မော်ဒယ်၊ retrieval သို့မဟုတ် tool ပြောင်းလဲမှုများ ပြီးနောက်တွင် အရေးပါသည်။ ထုတ်လုပ်မှု အကျိုးဆက် အရ ၎င်းသည် အရင် ပြင်ပြီးသား ပျက်ကွက်မှုတစ်ခုကို တိတ်ဆိတ်စွာ ပြန်လည် ဖြစ်ပေါ်ခြင်းမှ ကာကွယ်သည်၊ အကြောင်းမှာ AI စနစ် ပြောင်းလဲမှုများသည် ပျမ်းမျှ အရည်အသွေးကို မြှင့်တင်စဉ် ထို ပျက်ကွက်မှုကို ပြန်ယူလာနိုင်သည်။ Regression test သည် သတ်မှတ်ထားသည့် မျှော်လင့်အပြုအမူတစ်ခုကို ကာကွယ်သည်၊ ကျယ်ပြန့်သည့် benchmark သည် ပိုမို ကျယ်သည့် လုပ်ငန်း ပြန့်ကျဲမှုအပေါ် စွမ်းဆောင်ရည်ကို ခန့်မှန်းသည်။ လက်တွေ့တွင် ပြုပြင်ပြီးသား prompt-injection ဖြစ်ရပ်တစ်ခုကို အမြဲတမ်း eval case အဖြစ် ပြောင်းလဲပြီး၊ နောက် deployment မတိုင်မီ ၎င်း အောင်ရမည် ဖြစ်သည်။

#### Reproducible Build

Reproducible Build သည် ကြေညာထားသည့် source၊ ပတ်ဝန်းကျင် နှင့် လမ်းညွှန်ချက်များကို သီးခြားစီ ပြန်လည် လုပ်ဆောင်သည့်အခါ သတ်မှတ်ထားသည့် artifact များကို bit တစ်လုံးမျှ မကွာဘဲ တူညီစွာ ထုတ်လုပ်နိုင်သည့် build ဖြစ်သည်။ ထုတ်လုပ်မှု အကျိုးဆက် အရ ၎င်းသည် artifact တစ်ခုကို မူလ ထုတ်လုပ်ခဲ့သည့် စက် သို့မဟုတ် agent ကို ကျော်လွန်၍ စစ်ဆေးနိုင်စေပြီး၊ ဖုံးကွယ်နေသည့် build input များကို ဖော်ထုတ်ပေးသည်။ နှစ်ကြိမ် အောင်မြင်သည့် build သည် ထပ်လုပ်နိုင်သည့် အထောက်အထား ဖြစ်သည်၊ သို့သော် reproducibility အတွက် ကြေညာထားသည့် သီးခြား အခြေအနေများ နှင့် တူညီသည့် output များ လိုအပ်သည်။ လက်တွေ့တွင် toolchain နှင့် dependency များကို pin လုပ်ခြင်း၊ timestamp နှင့် မတည်ငြိမ်သည့် အစဉ်လိုက်မှုများကို ဖယ်ရှားခြင်း၊ ပတ်ဝန်းကျင်ကို မှတ်တမ်းတင်ခြင်း ပြုလုပ်ပြီး၊ သီးခြားစီ ပြန်လည် ထုတ်လုပ်သည့် artifact digest များကို နှိုင်းယှဉ်ရမည်။

## ၄။ လက်တွေ့ တွက်ချက်မှု သုံးခု

ဤအပိုင်းရှိ output အားလုံးသည် အောက်တွင် ဖော်ပြသည့် command များကို တကယ် run ၍ ရရှိသည့် ရလဒ်များ ဖြစ်သည်။ script များသည် standard library သာ အသုံးပြုပြီး deterministic ဖြစ်သည်။

```text
assumed repository: 900 files x 420 tokens/file = 378,000 context tokens
assumed task       : 6 agent rounds, 700 output tokens/round
assumed price      : USD 3.00 per 1M input tokens, USD 15.00 per 1M output tokens
assumed window     : 128,000 tokens
--------------------------------------------------------------------------
strategy            files   ctx tok/round    input tok  output tok   USD/task  fits

--------------------------------------------------------------------------
saving with retrieval-scoped context = USD 6.7133 per task (97.76%)
context the whole-repo strategy needs per round is 2x the window
မှတ်ချက် - whole-repo context သည် window ထဲ မဆံ့သောကြောင့် မဖြစ်နိုင်ပါ၊ scoped retrieval သည် token နှင့် ကုန်ကျစရိတ် နှစ်ခုလုံးကို လျှော့ချသည်။
==========================================================================
```

ရလဒ်က ပြသည့် အဓိက အချက်မှာ whole-repo context သည် round တစ်ခုလျှင် 378,000 token လိုအပ်ပြီး window ၏ နှစ်ဆ ဖြစ်နေခြင်းကြောင့် လုံးဝ မဖြစ်နိုင်ခြင်း ဖြစ်သည်။ retrieval-scoped context သည် USD 6.8670 မှ USD 0.1537 သို့ ကျဆင်းစေသည်၊ သို့သော် လိုအပ်သည့် အထောက်အထား မကျန်ခဲ့စေရန် တာဝန်သည် ရှာဖွေမှု အရည်အသွေး အပေါ် ရောက်သည်။

### (ခ) သတ်မှတ်ထားသည့် reviewer နှုန်း နှင့် defect နှုန်းအတွက် review budget

ဖော်မြူလာ — `review_minutes = generated_lines/100 * review_min_per_100`၊ `reviewable_lines = min(generated_lines, capacity/review_min_per_100*100)`၊ `defects_escaping = generated_lines*defect_rate - reviewable_lines*defect_rate*catch_rate`။ ယူဆချက် — ထုတ်လုပ်သည့် စာကြောင်း 1200၊ 100 စာကြောင်းလျှင် 25 review မိနစ်၊ defect နှုန်း 0.08၊ capacity 480 မိနစ်၊ စစ်ဆေးသည့်စာကြောင်းများတွင် ဖမ်းမိနိုင်သည့် နှုန်း 0.70၊ reviewer စျေးနှုန်း USD 60.00/hour။ ဤနှုန်း အားလုံးသည် ယူဆချက် ဖြစ်သည်။

ဤတန်ဖိုးများက ပေးသည့် အဓိက သတိပေးချက်မှာ လွတ်ထွက်သည့် defect အရေအတွက်သည် defect နှုန်း တစ်ခုတည်းအပေါ် မမူတည်ဘဲ reviewer ၏ capacity အပေါ်လည်း မူတည်ခြင်း ဖြစ်သည်။

### (ဂ) retry ပါဝင်သည့် cost per merged change

ဖော်မြူလာ — `expected_attempts = sum_{k=1..A} (1-p)^(k-1)`၊ `success_prob = 1-(1-p)^A`၊ `cost_per_attempt = tokens/Mtok*price + attempt_minutes/60*repo_hour_cost`၊ `cost_per_merged = total_attempts*cost_per_attempt / merged_changes`။ ယူဆချက် — လုပ်ငန်း 100 ခု၊ attempt ကန့်သတ်ချက် 4၊ attempt တစ်ခုလျှင် success rate 0.62၊ attempt တစ်ခုလျှင် token 9000၊ စျေးနှုန်း USD 3.00/Mtok၊ repo wall-clock USD 45.00/hour၊ attempt တစ်ခုလျှင် 6 မိနစ်။ ဤနှုန်း အားလုံးသည် ယူဆချက် ဖြစ်သည်။

```text
$ python3 guides/08_ai_native_development/scripts/ex_c_change_cost.py

==========================================================================
assumed work  : 100 tasks, attempt cap 4, success rate 0.620 per attempt
assumed usage : 9,000 tokens per attempt, USD 3.00 per 1M tokens
assumed infra : USD 45.00 per repo-hour, 6.0 minutes per attempt
--------------------------------------------------------------------------
cost per attempt (tokens)       : USD   0.0270
cost per attempt (wall-clock)   : USD   4.5000
cost per attempt (total)        : USD   4.5270
expected attempts per task      :       1.5793
success probability per task    :       0.9791
retries beyond first attempt     :        57.93
merged changes                  :        97.91

--------------------------------------------------------------------------
cost per merged change is 1.613x the cost of a single attempt
မှတ်ချက် - success rate နိမ့်လျှင် retry အရေအတွက် တိုးပြီး၊ merged change တစ်ခုလျှင် ကုန်ကျစရိတ် မြင့်သည်။
==========================================================================
```

ဤရလဒ်တွင် wall-clock စရိတ်သည် token စရိတ်ကို အလွန်အမင်း လွန်ကဲနေသည်ကို တွေ့နိုင်သည်၊ ဆိုလိုသည်မှာ ကျရှုံးသည့် attempt တိုင်းသည် လူ နှင့် repo အချိန် 6 မိနစ်ကို ဖြုန်းတီးနေခြင်း ဖြစ်သည်။ success rate ကို 0.45 သို့ လျှော့ချကြည့်လျှင် merged change တစ်ခုလျှင် ကုန်ကျစရိတ်သည် USD 10.0600 အထိ တက်သည်၊ မှားယွင်းသည့် အဖြေ တစ်ခုကို စောစော ဖမ်းမိခြင်း၏ တန်ဖိုးကို ဤခြားနားမှုက ဖော်ပြသည်။

## ၅။ ဤနယ်ပယ်မှ ဆင်းသက်လာသည့် ထုတ်လုပ်မှု ဆုံးဖြတ်ချက် ခြောက်ခု

**၁။ Context strategy သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Progressive Disclosure၊ Repository Map၊ Repository Instructions။ သက်သေပြသည့် မက်ထရစ် — strategy အလိုက် context token နှင့် USD/task။ ဥပမာ (က) က whole-repo context သည် window ၏ နှစ်ဆ လိုအပ်သည်ဟု ပြသည်၊ ထို့ကြောင့် context ကို "အားလုံး" ဟု မသတ်မှတ်ရ၊ အဆင့်လိုက် ဖော်ထုတ်သည့် မူဝါဒ အဖြစ် သတ်မှတ်ရမည်။

**၂။ Review capacity သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Reviewer Agent၊ Patch၊ Flaky Test။ သက်သေပြသည့် မက်ထရစ် — review မိနစ်၊ queue နှင့် လွတ်ထွက်သည့် defect အရေအတွက်။ ဥပမာ (ခ) အရ 1200 စာကြောင်းသည် 300 review မိနစ် လိုအပ်သည်၊ capacity 480 မိနစ်တွင် ဆံ့သည်၊ သို့သော် ထုတ်လုပ်မှု 3000 စာကြောင်းသို့ တက်လျှင် queue ဖြစ်ပေါ်ပြီး လွတ်ထွက်သည့် defect တိုးသည်။

**၃။ Agent work packet သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Scope Contract၊ Handoff၊ Worktree။ သက်သေပြသည့် မက်ထရစ် — packet တွင် ပါသည့် အထောက်အထား အရေအတွက် နှင့် ထပ်လုပ်ရသည့် အလုပ် ရာခိုင်နှုန်း။ ၎င်းသည် လုပ်ငန်း တစ်ခုကို session ပြောင်းသည့်အခါ context ပြန်လည် ဖန်တီးရသည့် ကုန်ကျစရိတ်ကို ကန့်သတ်သည်။

**၄။ Retry policy သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Retry with Backoff၊ Idempotency၊ Rate Limit၊ Backpressure။ သက်သေပြသည့် မက်ထရစ် — attempt ကန့်သတ်ချက်နှင့် အလိုက် retry အရေအတွက်။ ဥပမာ (ဂ) က cap 4 ဖြင့် ပိုလျှံသည့် attempt 57.93 ခု ဖြစ်သည်ဟု ပြသည်၊ ထို့ကြောင့် cap ကို cost per merged change နှင့် တွဲဖက် သတ်မှတ်ရမည်။

**၅။ Verification gate သတ်မှတ်ခြင်း** — မှီခိုသည့် term များ — Test Oracle၊ Regression Test၊ Reproducible Build၊ Observability။ သက်သေပြသည့် မက်ထရစ် — အလိုအလျောက် classify လုပ်နိုင်သည့် ရလဒ် ရာခိုင်နှုန်း နှင့် gate ကျရှုံးသည့် အရေအတွက်။ ထို အချိုးသည် လူ ပါဝင်ရမည့် review တန်းကို ဆုံးဖြတ်သည်။

**၆။ ကုန်ကျစရိတ် တာဝန် ခွဲခြားခြင်း (cost attribution)** — မှီခိုသည့် term များ — Cost per Successful Task၊ Trace၊ Coding Agent၊ Model Router၊ Semantic Cache။ သက်သေပြသည့် မက်ထရစ် — merged change တစ်ခုလျှင် ကုန်ကျစရိတ် (token နှင့် wall-clock ခွဲခြား၍)။ ဥပမာ (ဂ) က ဤမက်ထရစ်ကို USD 7.3016 အဖြစ် တွက်ပြသည်၊ ၎င်းကို merged change အရေအတွက်ဖြင့်သာ တိုင်းရမည်၊ လုပ်ဆောင်သည့် attempt အရေအတွက်ဖြင့် မတိုင်းရ။
